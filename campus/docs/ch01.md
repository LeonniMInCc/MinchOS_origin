# 第 1 章　从上电到 Rust

> 对应 tag `v0.1`。本章代码：`git show v0.1`

## 1.1 这一章要解决的问题

写操作系统的第一个障碍不是"写什么"，而是**"我的代码凭什么会被执行"**。

平时写 Rust，`fn main()` 会被调用，是因为底下有一整套东西：操作系统的加载器把
程序读进内存、建好地址空间、准备好栈，C 运行时初始化完 `.bss` 和全局变量，
最后才轮到 `main`。

现在我们要写的**就是那个操作系统**。所有这些服务都不存在。本章要做的就是
亲手把这条链路从头接起来。

## 1.2 启动链路

QEMU `virt` 机器上电后：

```
QEMU 复位向量
     │
     ▼
OpenSBI  (M 态, 加载于 0x80000000)
     │   ← 初始化 PMP、委托中断、打印 banner
     ▼
CCNUOS   (S 态, 加载于 0x80200000)
     │
     ├─ entry.asm : la sp, boot_stack_top
     │              call rust_main
     ▼
rust_main() : clear_bss() → 打印 → shutdown()
```

**OpenSBI 是什么？** 它是运行在 M 态（机器态，RISC-V 最高特权级）的固件，
对上层提供一组标准服务 —— 串口输出、关机、设时钟。我们的内核跑在 S 态，
碰不到硬件寄存器，只能通过 `ecall` 指令请它代劳。这层接口叫 **SBI**
(Supervisor Binary Interface)，地位相当于 x86 世界里的 BIOS/UEFI 运行时服务。

**为什么是 0x80200000？** 这是 SBI 与内核之间的约定：固件自己占用
`0x80000000` 起的一段（QEMU 11 自带的 OpenSBI v1.8.1 占 321 KB），
把 `0x80200000` 留给下一级。这个地址写在 `os/src/linker.ld` 的
`BASE_ADDRESS` 里，**必须**和固件的预期一致，差一个字节都起不来。

## 1.3 四块拼图

### `linker.ld` —— 决定字节落在哪

链接脚本干两件事：

1. 把 `.text.entry` 段放在 `BASE_ADDRESS`，保证固件跳过来时第一条指令就是我们的入口。
2. 导出一批符号（`stext`、`ebss`、`ekernel` …），让 Rust 代码能反过来知道自己的布局。

有一处安排值得注意：

```ld
sbss_with_stack = .;
.bss : {
    *(.bss.stack)     /* 启动栈排在前面 */
    sbss = .;
    *(.bss .bss.*)
}
```

启动栈也在 `.bss` 里，但被刻意排在 `sbss` **之前**。因为清零 `.bss` 的那段
Rust 代码自己正跑在这个栈上 —— 把它一起清了，等于锯自己坐着的树枝。

### `entry.asm` —— 支起栈

```asm
_start:
    la      sp, boot_stack_top
    call    rust_main
```

只有两条指令。**Rust 的任何函数调用都需要栈**（保存返回地址、存放局部变量），
而固件跳过来时 `sp` 的值是未定义的。所以必须先有这两行汇编，才谈得上进 Rust。

### `sbi.rs` —— 向下请求服务

```rust
asm!(
    "ecall",
    inlateout("a0") arg0 => error,
    inlateout("a1") arg1 => value,
    in("a2") arg2,
    in("a6") fid,      // Function ID
    in("a7") eid,      // Extension ID
);
```

`ecall` 会触发一次同步异常，把控制权交给更高特权级。参数放哪个寄存器、
返回值从哪里取，都由 SBI 规范规定。这段代码是本章最"接近硬件"的地方 ——
**它是内核向下层求助的唯一通道**。

我们没有用现成的 `sbi-rt` crate。对教学项目来说，亲眼看见 `ecall` 怎么发生，
比省下这四十行代码值钱得多。

### `console.rs` —— 把 `println!` 接上

Rust 的 `format_args!` 机制是和 `core::fmt::Write` trait 解耦的。只要给一个
类型实现 `write_str`，整套格式化能力就能白嫖：

```rust
struct Stdout;   // 零大小类型，不占内存，只是 trait 实现的挂载点

impl Write for Stdout {
    fn write_str(&mut self, s: &str) -> fmt::Result {
        for byte in s.bytes() {
            console_putchar(byte as usize);
        }
        Ok(())
    }
}
```

## 1.4 本章踩的三个坑

这三个都是真实卡住过的地方，记录下来比记录成功路径有用。

### 坑 1：`--manifest-path` 不读 `.cargo/config.toml`

```
error: invalid register `a0`: unknown register
```

看起来像是内联汇编写错了，实际上是**编译目标不对** —— 它在按 aarch64 编译，
而 aarch64 当然没有 `a0` 寄存器。

根因：`cargo` 是按**当前工作目录**向上查找 `.cargo/config.toml` 的。
在仓库根目录执行 `cargo build --manifest-path os/Cargo.toml`，
`os/.cargo/config.toml` 里的 `target = "riscv64gc-unknown-none-elf"` 会被完全忽略。

修法：Makefile 里老老实实 `cd os && cargo build`。

### 坑 2：`-device loader` 配 fw_dynamic 固件不工作

OpenSBI 的 banner 正常打出来了，但内核一个字都没输出，QEMU 就此挂住。
关键线索藏在 banner 里：

```
Domain0 Next Address        : 0x0000000000000000
```

固件不知道下一级该跳到哪。`-device loader,file=...,addr=0x80200000` 只是把字节
搬进内存，并不会告诉固件这件事。而 QEMU 11 自带的 OpenSBI 是 **fw_dynamic**
形态，它的跳转地址要靠 QEMU 在启动时填进来。

修法：改用 `-kernel`。QEMU 会把内核加载到 `0x80200000` **并且**把这个地址
写进传给 OpenSBI 的启动信息里。

> 很多教程（包括 rCore 的老版本）用的是 `-device loader` + 独立的 `rustsbi-qemu.bin`，
> 那是 fw_jump 形态的固件，跳转地址是编译时固定的，所以能工作。
> 换到新 QEMU 自带的 OpenSBI 上就会踩这个坑。

### 坑 3：按 `char` 输出导致中文乱码

```
CCNUOS v0.1.0  RISC-V 64 (SV39) Yf\
```

`console_putchar` 一次只接受一个**字节**。而按 `char` 遍历时，
`c as usize` 拿到的是 Unicode 码点（"内" = `0x5185`），送进 SBI 只有低 8 位
被写出，多字节字符就碎了。

修法：`s.bytes()` 而不是 `s.chars()`，把 UTF-8 原样丢给终端去重组。

**第 6 周做页帧分配器时，可用物理内存就从这个地址开始算**。

## 1.6 练习

1. **把启动栈改小到 4 KiB**，然后在 `rust_main` 里写一个递归很深的函数。观察会发生什么 ——
   你会发现它默默地把 `.bss` 写坏了，而不是报错。这就是为什么第 8 周要给内核栈加 guard page。
2. **`make asm`** 反汇编内核，找到 `_start`，确认它确实位于 `0x80200000`。
3. **把 `clear_bss` 的范围改成 `sbss_with_stack..ebss`**，看看会怎样崩。想清楚为什么。
4. **在 `sbi.rs` 里加一个 `get_spec_version`**（EID `0x10`, FID `0`），把固件的 SBI 版本打出来。

## 1.7 下一章

第 2 章要解决的是：**内核里怎么用 `Vec`**。

裸机上没有 `malloc`。我们需要划一块静态内存当堆，写一个分配器，
挂到 `#[global_allocator]` 上，`alloc` crate 的所有容器才能用起来。
