# 第 4 章　多道程序：让任务轮流跑

> 对应 tag `v0.4`。本章代码：`git diff v0.3..v0.4`

## 4.1 这一章要解决的问题

第 3 章的批处理系统有个硬伤：**一个程序不跑完，下一个就没机会**。
程序等磁盘、等键盘的时候，CPU 只能干等着。

这一章让多个程序**同时待在内存里**，通过 `sys_yield` 主动让出 CPU，轮流执行。
这是"并发"的第一步 —— 虽然只有一个 CPU，但从外部看，多个程序在同时推进。

## 4.2 三件必须先做的事

### 一、所有程序同时装入内存

第 3 章是"用一个装一个，装新的覆盖旧的"。现在要一次性全装进去，各占一个
128 KiB 的槽位：

```text
  0x80400000  程序 0
  0x80420000  程序 1
  0x80440000  程序 2
  ...
```

### 二、每个程序必须链接到不同的地址

这是"没有分页"带来的直接代价。程序里的每一个绝对地址 —— 函数地址、全局变量、
字符串字面量 —— 在**链接时**就写死了。一个链接到 `0x80400000` 的程序，
放到 `0x80420000` 上运行会立刻跳到错误的地方。

所以必须为每个程序单独生成一份链接脚本，逐个编译。这就是
`tools/build-user.py` 存在的理由：（**这个脚本已经不在了** —— 第 8 周有了跳板页和独立地址空间之后，所有用户程序链接到同一个地址，它就退休了。见 [第 8 章](ch08.md)。）


```
编译 8 个用户程序：
  [0] 00hello_world        base=0x80400000    4829 字节
  [1] 01yield_a            base=0x80420000    4712 字节
  [2] 02yield_b            base=0x80440000    4712 字节
  ...
```

> 脚本里有一行容易被忽略但很关键：编译每个程序前要**删掉上一次的产物**。
> 不删的话 cargo 只看源码有没有变，会直接复用旧二进制 —— 于是程序 3 带着
> 程序 0 的基址跑起来，症状是启动即跑飞，而且构建日志一切正常。
>
> 第 7 周引入分页后，这个脚本就可以退休了：所有程序都能以为自己独占
> `0x80400000`，而实际占用互不相同的物理页。

### 三、每个任务要有自己的内核栈

这一条值得想清楚。为什么不能共用一个内核栈？

因为任务的执行可以**交错**：程序 A 陷入内核、还没处理完就切到了程序 B。
A 在内核里的执行状态 —— 局部变量、调用链、返回地址 —— 必须原样留在
某个地方，等它被调度回来时接着用。共用一个栈的话，B 会直接把 A 的栈帧盖掉。

所以：**N 个任务 = N 个用户栈 + N 个内核栈**。

## 4.3 `TaskContext`：为什么只有 14 个寄存器

第 3 章的 `TrapContext` 要存 34 个寄存器，这一章的 `TaskContext` 只存 14 个。
差别从哪来？

| | `TrapContext` | `TaskContext` |
|---|---|---|
| 触发方式 | 硬件异常，**随时可能发生** | `__switch` 是个普通函数调用 |
| 被打断的是谁 | 用户程序，毫不知情 | 内核自己，主动调用 |
| 要保存什么 | 全部 32 个通用寄存器 | 只有 callee-saved |

`__alltraps` 面对的是"用户程序执行到任意一条指令时被硬件打断"。那一刻每个寄存器
里都可能存着有用的值，少存一个就毁掉了现场。

而 `__switch` 是**内核代码主动调用的一个函数**。按 RISC-V 调用约定，调用方在调用
任何函数前，就已经把自己还需要的 caller-saved 寄存器（`t0`~`t6`、`a0`~`a7`）
妥善安置了 —— 这是编译器保证的。`__switch` 作为被调用者，只要守住自己这一侧的
约定：保存 `s0`~`s11`、`ra`、`sp`。

**编译器已经替我们干了一半的活。** 认出"哪些约定可以借力"，是内核代码能写得短的原因。

## 4.4 `ra`：一个字段，两种语义

`TaskContext` 里最关键的是 `ra` —— 它决定"这个任务下次被调度时从哪里继续"：

- **第一次**被调度：`ra = __restore`，于是任务从内核态返回用户态，
  开始执行程序的第一条指令
- **之后**被调度：`ra` 指向它上次调用 `__switch` 的下一条指令，
  于是它从"让出 CPU 的那一刻"继续往下跑

同一个字段，两种语义，一套代码 —— 和第 3 章"启动程序 = 从一次不存在的 trap 返回"
是完全相同的思路。内核里这种"用一套机制覆盖两种场景"的设计到处都是。

## 4.5 `__switch`：从一个任务进去，从另一个任务出来

```asm
__switch:
    sd sp, 8(a0)        # 存当前
    sd ra, 0(a0)
    ... 存 s0-s11 ...
    ld ra, 0(a1)        # 载入下一个
    ... 载入 s0-s11 ...
    ld sp, 8(a1)
    ret
```

代码平淡，但性质反直觉：**它从一个任务进去，从另一个任务出来。**

最后那条 `ret` 返回到的，是任务 B 上次调用 `__switch` 的位置。调用它的任务 A
的执行流就停在这里了，直到将来某个任务再 `__switch` 回它。

从 Rust 侧看，`__switch(a, b)` 就是一次普通的函数调用，会正常返回。但"返回"的
那一刻可能已经过去了很久，中间跑过了别的任务。这种**时间上不连续的返回**是内核
代码的常态。

顺着这个往下想，`sys_yield` 的整条链路是：

```text
用户程序 yield_now()
  → ecall → __alltraps → trap_handler → sys_yield
    → suspend_current_and_run_next → schedule_next
      → __switch  ←─────────── 执行流在这里断开
      ...（跑了别的任务）...
      → __switch 返回 ←─────── 被调度回来
    ← schedule_next 返回
  ← sys_yield 返回 0
  ← trap_handler 把 0 写进 cx.x[10]
  → __restore → sret → 用户程序从 yield_now() 的下一行继续
```

整条调用链自始至终待在**这个任务自己的内核栈**上，所以 `__switch` 只要存好
`sp`，整条链就能原封不动地恢复。

## 4.6 一处必须删掉的指令

第 3 章的 `__restore` 开头有一条：

```asm
mv sp, a0
```

因为那时 `__restore` 是被 Rust 当普通函数调用的，上下文地址通过 `a0` 传进来。

改成任务切换模型后，这条指令**必须删掉**。两条进入路径的 `sp` 都已经是对的：

- 从 `__alltraps` 落下来：`call trap_handler` 按调用约定会把 `sp` 原样还回来，
  它仍指向 `__alltraps` 腾出的那块 `TrapContext`
- 从 `__switch` 的 `ret` 跳进来：`sp` 是从 `TaskContext` 里加载的，
  正是 `init_app_cx` 压入 `TrapContext` 后的栈顶

留着这条指令的话，任务第一次被调度时会把 `sp` 设成 `__switch` 遗留在 `a0` 里的
垃圾值 —— 然后一切都完了，而且没有任何报错。

这类"改了模型之后某条老指令悄悄变成错的"是内核重构时最危险的一类 bug。

## 4.7 运行轨迹：协作式调度的弱点被演出来了

```
[INFO ] 任务管理器就绪：8 个任务，协作式轮转调度
你好，我是跑在 U 态的第一个用户程序。
[INFO ] 任务 0 正常退出，退出码 0
  [A] 第 0 轮 —— 让出 CPU
  [B] 第 0 轮 —— 让出 CPU
  [C] 第 0 轮 —— 让出 CPU
  [霸占者] 我要连算 30000 次乘法，中途一次都不 yield。
  [霸占者] 3^10000 mod 998244353 = 942248388
  [霸占者] 3^20000 mod 998244353 = 692358339
  [霸占者] 3^30000 mod 998244353 = 813516892
  [霸占者] 算完了，现在才轮到别人。
[INFO ] 任务 4 正常退出，退出码 0
... 任务 5/6/7 依次执行，其中两个作恶的被杀 ...
  [A] 第 1 轮 —— 让出 CPU
  [B] 第 1 轮 —— 让出 CPU
  [C] 第 1 轮 —— 让出 CPU
  [A] 第 2 轮 —— 让出 CPU
  ...
[INFO ] 没有就绪任务了，全部执行完毕，关机
```

这段输出里有三件事值得读：

**一、轮转确实在工作。** A → B → C → A → B → C 的交替说明调度器在按预期换人。

**二、上下文被精确保留了。** A 打完"第 0 轮"就让出，中间隔了霸占者的三万次乘法
和另外三个程序（其中两个还崩了），等它被调度回来时，循环计数器仍然是 1 ——
分毫不差。这是 `__switch` 正确性最直接的证据。

**三、协作式调度是脆弱的。** 霸占者拿到 CPU 后一次都不 yield，于是 A/B/C
**明明处于就绪状态却动不了**，只能等它算完。这不是 bug，这就是协作式调度的定义：
**调度器完全依赖任务自觉**。

把霸占者的主体换成 `loop {}`，整个系统就永远卡死 —— 内核没有任何手段抢回控制权。
这正是第 5 周必须引入时钟中断的理由。

## 4.8 陷入内核 ≠ 让出 CPU

霸占者中途调了三次 `println!`，每次都陷入了内核。但它**没有**让出 CPU：
内核打印完就通过 `__restore` 回到了同一个任务。

这两件事要分清楚：

- **陷入内核**：特权级从 U 变 S，执行流还是同一个任务的
- **让出 CPU**：调用 `__switch`，执行流换成了另一个任务

只有 `sys_yield`、`sys_exit`，以及第 5 周的时钟中断，才会触发第二件事。

## 4.9 内存账单

8 个任务，每个一套栈：

```
用户栈   8 KiB × 16 槽位 = 128 KiB
内核栈   8 KiB × 16 槽位 = 128 KiB
程序槽位 128 KiB × 8      = 1 MiB
```

栈是按 `MAX_APP_NUM` 静态分配的，所以哪怕只跑 8 个程序，16 个槽位的栈也都占着。
第 9 周引入动态进程创建后，这些会改成按需从堆上分配。

## 4.10 练习

1. **把 `04power_hog` 的主体换成 `loop {}`**，观察整个系统卡死。
   这是本章最有说服力的一个实验 —— 你需要 `Ctrl-A` `X` 才能退出。
2. **删掉 `trap.S` 里 `__restore` 的 `mv sp, a0` 之前的版本**（`git show v0.3`），
   把它加回来，看第一个任务是怎么跑飞的。用 GDB 在 `__restore` 下断点，
   对比 `sp` 和 `a0` 的值。
3. **改调度算法**：把轮转改成"总是选编号最小的就绪任务"，
   观察 A/B/C 的输出变成什么样。想想这种策略的问题是什么。
4. **在 `tools/build-user.py` 里注释掉 `unlink` 那一行**，然后交换两个程序的
   文件名前缀重新构建。你会看到程序带着错误的基址启动 —— 这就是那行注释
   警告的情况。
5. **统计切换次数**：在 `schedule_next` 里加一个计数器，退出时打印总切换次数。
   和第 5 周时间片轮转的数字对比会很有意思。

## 4.11 下一章

第 5 章：**抢占式调度**。

给 CPU 装上闹钟 —— SBI 的 `set_timer` 加上 `sie` 里的时钟中断使能。
每隔一个时间片，硬件强行把控制权交还内核，内核就能把 CPU 从任何一个任务手里
夺回来，哪怕它正在 `loop {}`。

到那时，`UPSafeCell` 上记的那笔账就要还了：中断处理程序可能在临界区中间插进来，
"单核且不被抢占"的前提会失效。
