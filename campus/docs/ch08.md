# 第 8 章　跳板页：每个进程一个地址空间

> 对应 tag `v0.8`。本章代码：`git diff v0.7..v0.8`
>
> 全项目最难的一周。做完之后，CCNUOS 才算有了真正的内存隔离。

## 8.1 这一章要解决的问题

第 7 章建了**一个**恒等映射的地址空间，内核和用户共用。那已经带来了一层
保护（用户的页带 `U`，内核的不带），但本质上所有进程还是住在同一个房子里 ——
只是各自房间的门锁着。

这一章要让**每个进程有自己的房子**。

麻烦立刻就来了：trap 发生时，CPU 还在用户的页表上，而内核代码在另一个地址
空间里。必须换页表。而换页表这件事，有一个致命的时序问题。

## 8.2 那条要命的指令

```asm
csrw satp, t0
```

**这条指令执行完之后，取下一条指令用的已经是新页表了。**

如果新页表里没有"当前正在执行的这段代码"，PC 立刻指向一片虚空。
而且此时连 trap 都处理不了 —— `stvec` 指向的地址在新页表里同样不存在 ——
CPU 直接卡死，没有任何报错。

这不是普通的 bug，是**连调试都无从下手**的那种。

## 8.3 跳板页

解法出奇地简单，但需要想通：

> 把执行切换的那段代码单独放一页，在**每一个**地址空间里都映射到
> **完全相同的虚拟地址**上。

这样 `satp` 一换，PC 指向的还是同一页 —— 因为两边的页表都在那个虚拟地址上
映射了它（只是映射到同一个物理页而已）。切换是无缝的。

这一页就叫**跳板**(trampoline)，放在整个 64 位地址空间的最后一页：

```rust
pub const TRAMPOLINE: usize = usize::MAX - PAGE_SIZE + 1;  // 0xFFFF_FFFF_FFFF_F000
```

选最高那页是因为它离用户程序的地址范围最远，不会撞上。

实现上要做三件事：

1. `linker.ld` 里给 `.text.trampoline` 段前后加 `ALIGN(4K)`，让它独占一页
   —— 不然映射跳板时会连带把别的内核函数也暴露出去
2. `trap.S` 里 `__alltraps` / `__restore` 放进这个段
3. 每个 `MemorySet`（内核的和每个进程的）都调 `map_trampoline()`

权限是 `R | X`，**没有 `U`** —— 这段代码运行在 S 态。给了 `U` 的话，
用户程序就能直接跳进 `__restore` 自己切页表了。

## 8.4 `TrapContext` 多出来的三个字段

`__alltraps` 要换页表，它得知道：内核的 `satp`、内核栈在哪、`trap_handler` 在哪。

这三样信息，在那个时刻：

- **不能放在寄存器里** —— 寄存器正要被保存，动不得
- **不能从内核的数据结构读** —— 还没切到内核页表，读不到

唯一的出路是**预先写进 `TrapContext`**：

```rust
pub struct TrapContext {
    pub x: [usize; 32],
    pub sstatus: usize,
    pub sepc: usize,
    pub kernel_satp: usize,   // ← 新增
    pub kernel_sp: usize,     // ← 新增
    pub trap_handler: usize,  // ← 新增
}
```

`trap_return` 在返回用户态之前填好，`__alltraps` 陷入时直接读出来。

这是一个很典型的内核设计手法：**当某个时刻拿不到需要的信息时，
就在更早的、还拿得到的时刻把它存下来。**

## 8.5 `sscratch` 换了含义

| | 第 3–7 周 | 第 8 周起 |
|---|---|---|
| U 态运行时 `sscratch` | 内核栈顶 | `TRAP_CONTEXT`（固定虚拟地址） |

为什么变？因为内核栈现在在**另一个地址空间**里，用户页表下根本访问不到。
而 `TrapContext` 被钉在每个进程地址空间的固定虚拟地址上（跳板页下面一页），
`sscratch` 存它正合适。

于是 `__alltraps` 开头那条 `csrrw sp, sscratch, sp` 之后，`sp` 直接指向
`TrapContext` —— 连第 3 周那条 `addi sp, sp, -34*8` 都省了。

## 8.6 完整的路径

```text
  用户程序（用户地址空间）
    │ ecall / 异常 / 时钟中断
    ▼
  __alltraps  ← 跳板页，两个地址空间里同一个虚拟地址
    │ csrrw sp, sscratch, sp   →  sp 指向 TRAP_CONTEXT
    │ 保存 32 个寄存器 + sstatus + sepc
    │ 从 TrapContext 读出 kernel_satp / kernel_sp / trap_handler
    │ csrw satp, kernel_satp    ★ 换地址空间
    │ sfence.vma
    │ jr trap_handler
    ▼
  trap_handler（内核地址空间，跑在本任务的内核栈上）
    │ 分派：系统调用 / 杀进程 / 重新调度
    ▼
  trap_return
    │ stvec ← TRAMPOLINE
    │ 算出跳板页里 __restore 的虚拟地址
    │ jr 过去，a0 = TRAP_CONTEXT，a1 = 用户 satp
    ▼
  __restore   ← 还是那一页
    │ csrw satp, a1             ★ 换回去
    │ 恢复现场
    │ sret
    ▼
  用户程序
```

有一处容易写错：`trap_return` 里**不能直接 `call __restore`**。那会跳到
`__restore` 的**链接地址**（在内核 `.text` 里），而马上就要换成用户页表了，
那个地址在用户空间里不存在。必须算出它在跳板页里的虚拟地址：

```rust
let restore_va = __restore as usize - __alltraps as usize + TRAMPOLINE;
```

跳板页是整段搬过去的，所以相对偏移在两个地址空间里完全一样。

## 8.7 一个进程的地址空间长什么样

```text
  0x00010000  ELF 各段    代码 R-X U / 只读 R-- U / 数据 RW- U
              ...
              [guard page]           ← 不映射，栈写穿立刻缺页
              用户栈       RW- U
              ...
  ...FFFE000  TrapContext  RW-       ← 没有 U！
  ...FFFF000  跳板页       R-X       ← 没有 U！
```

**`TrapContext` 页不给 `U`** 这一条值得单说。它是内核用来保存/恢复这个进程
现场的地方 —— 如果用户能写它，就能改自己的 `sepc` 和 `sstatus`，
等于可以任意跳转、甚至把 `SPP` 改成 S 态来提权。

内核地址空间则是：

```text
  0x80200000  .text        R-X       ← 内核代码不可写
              .rodata      R--
              .data/.bss   RW-       ← 数据段不可执行
              可用物理内存  RW-       ← 恒等映射，内核靠它读写任意物理页
              ...
              任务 N 内核栈 RW-  ┐
              [guard page]      ├ 从跳板页往下依次排布
              任务 0 内核栈 RW-  ┘
  ...FFFF000  跳板页       R-X
```

**内核空间里没有任何一页带 `U`。** 这正是隔离的意义。

## 8.8 内核栈的 guard page

内核栈从跳板页往下排，每两个之间留一页不映射：

```rust
pub const fn kernel_stack_position(app_id: usize) -> (usize, usize) {
    let top = TRAMPOLINE - PAGE_SIZE - app_id * (KERNEL_STACK_SIZE + PAGE_SIZE);
    (top - KERNEL_STACK_SIZE, top)
}
```

内核栈溢出是最难查的一类 bug：症状会出现在另一个任务的数据上，现场和起因
毫无关系。一页地址空间换一个"立刻崩在现场"，非常划算。

实测（临时在 `trap_handler` 里往栈底下方写一个字）：

```
[INFO] 内核栈 [0xffffffffffffc000, 0xffffffffffffe000)，现在去写它下面的 guard page
[KERNEL PANIC] 内核自身触发了 trap：Exception(StorePageFault)
               scause=0xf  stval=0xffffffffffffbff8  sepc=0x80204fbc
```

`stval` 正是越界的那个地址。注意能看到这么清楚的现场，靠的是**第 7 章加的
`__kernel_trap`** —— 那时它还派不上什么用场，这一章立刻兑现了价值。

## 8.9 `SUM` 关掉了，而且是以更好的方式

第 7 章因为内核和用户共用地址空间，不得不打开 `sstatus.SUM`（允许 S 态访问
带 `U` 的页），失去了一层保护。

现在两者的地址空间彻底分开，内核连用户的地址都解引用不了 ——
`0x10234` 在内核页表里根本不存在。所以必须手动走一遍用户的页表：

```rust
pub fn translated_byte_buffer(token, ptr, len) -> Option<Vec<&'static mut [u8]>>
```

这个改变顺带把安全检查也做好了，而且比以前干净得多：

| | 第 3–7 周 | 第 8 周 |
|---|---|---|
| 怎么问 | "这个地址落在我划的那几个区间里吗" | "**用户自己的页表里，这页带 `U` 吗**" |
| 需要知道 | `APP_BASE_ADDRESS`、`APP_SIZE_LIMIT`、栈区边界…… | 什么都不用 |
| 溢出处理 | 手写 `checked_add` | 还是要，但只有一处 |
| 漏一种情况的风险 | 高 | 低 —— 页表本来就是权威 |

**把权限问题交还给权限系统本身。** 这是本章第二个值得记住的设计思路。

`is_accessible_by` 那个手写的区间检查因此被删掉了。

## 8.10 隔离的直接证明

光看地址推断是不够的。`01yield_a` / `02yield_b` / `03yield_c` 三个程序被
链接到**完全相同的虚拟地址**，各自有一个全局变量 `MARK`，每轮打印它的
地址和值：

```
  [A] 第 0 轮：MARK @ 0x13000 = 0xaaaa —— 让出 CPU
  [B] 第 0 轮：MARK @ 0x13000 = 0xbbbb —— 让出 CPU
  [C] 第 0 轮：MARK @ 0x13000 = 0xcccc —— 让出 CPU
  [A] 第 1 轮：MARK @ 0x13000 = 0xaaaa —— 让出 CPU
  ...
  [A] 四轮跑完，MARK 始终是 0xaaaa，隔离完好
```

**同一个虚拟地址 `0x13000`，三个不同的值，四轮下来一个都没变。**
这就是地址空间隔离的定义。

而那个越权写内核的程序，故障地址也从物理地址变成了用户地址：

```
第 7 周：StorePageFault，地址 0x80200000，指令位于 0x80940080  ← 物理地址
第 8 周：StorePageFault，地址 0x80200000，指令位于 0x10080     ← 用户虚拟地址
```

> **一个观察**：输出偶尔会在半行处交错，比如
> `[B] 第 1 轮：MARK @ 0x13000 = 0xbbbb  [C] 第 1 轮：...`。
> 这不是 bug —— `println!` 会拆成好几次 `sys_write`，中间被时钟中断
> 抢走 CPU 是完全正常的。想让一行输出成为原子操作，需要一把锁，
> 那是第 14 章的事。

## 8.11 反而变简单的地方

跳板页是这一周最复杂的东西，但它**让别的地方大幅简化了**：

| | 第 7 周 | 第 8 周 |
|---|---|---|
| `tools/build-user.py` | 130 行，逐个程序改基址重新链接 | **删掉了**，`cargo build` 一条命令 |
| `user/src/linker.ld` | 基址靠 `--defsym` 传进来 | 写死 `0x10000`，所有程序都一样 |
| `loader.rs` | 210 行：物理槽位、内核栈数组、用户栈数组、区间检查 | 45 行：只负责找出 ELF 的字节 |
| `is_accessible_by` | 手写区间算术 | 删掉，查页表 |
| `sstatus.SUM` | 必须打开 | 保持关闭 |

**多出来的一层间接（页表），反而让上层少了一整套机制。**
好的抽象就长这样。

## 8.12 又踩了同一个坑：cargo 不管链接脚本

改完链接脚本（基址从 `0x80800000` 改成 `0x10000`）重新构建，日志全绿。
但内核一跑，两个程序的故障 PC 还是旧地址。`objdump` 一查，它们的入口
确实还是 `0x80500000` / `0x80520000`。

根因和第 6 章**完全相同**：

> **cargo 不把链接脚本当作构建输入。** 链接脚本只是通过
> `-Clink-arg=-T...` 传给链接器的一个字符串，改了它 cargo 照样认为
> 产物是新鲜的，直接复用缓存。

第 6 章我是把基址塞进 `RUSTFLAGS` 绕过去的（cargo 的指纹包含 RUSTFLAGS）。
这一章基址回到了链接脚本里，问题就回来了 —— 而且更隐蔽，因为只有**部分**
程序命中了旧缓存，另一部分是新的，日志看起来完全正常。

这次不再靠"记得删文件"这种纪律，而是加了两道防线：

1. `user/build.rs` 里 `cargo:rerun-if-changed=src/linker.ld` —— 告诉 cargo
   这是个输入
2. **Makefile 构建后核对每个 ELF 的入口地址**，不对就大声失败并提示
   `make clean-user`

第 2 条才是真正靠得住的那个。第 1 条依赖 cargo 的内部行为（build script
重跑不一定触发重新链接），第 2 条**直接检查产物本身**。

> 教训：**构建系统告诉你"成功了"，不等于产物是对的。**
> 对于"某个属性必须成立"的产物（入口地址、段权限、大小上限），
> 值得花几行 shell 去实际验一遍。

## 8.13 练习

1. **把 `map_trampoline()` 从 `new_kernel()` 里删掉**（保留用户空间的），
   观察会发生什么。提示：`trap_return` 里那条 `jr restore_va` 是在内核
   地址空间里执行的。
2. **给跳板页加上 `U` 权限**，然后写一个用户程序直接 `jr` 到 `TRAMPOLINE`。
   想清楚它能做到什么 —— 这就是为什么那一位不能给。
3. **给 `TrapContext` 页加上 `U` 权限**，写一个用户程序去改自己的 `sstatus`，
   把 `SPP` 置 1。它能提权成功吗？
4. **把 `kernel_stack_position` 里的 `+ PAGE_SIZE`（guard page）去掉**，
   然后故意写穿一个内核栈，看它是怎么悄悄破坏隔壁任务的。
5. **在 `translated_byte_buffer` 里去掉 `PTEFlags::U` 的检查**，
   然后用 `07bad_syscall_arg` 试试能不能把内核内存打印出来。
6. **算一算**：11 个进程，每个的页表占多少页？用
   `MemorySet::page_table_frames()` 打印出来，和第 6 章那条
   "映射越稀疏、页表越大"的规律对照。

## 8.14 下一章

第 9 章：**进程管理**。

有了独立的地址空间，`fork` 才有意义 —— 它要复制一整个 `MemorySet`。
还要引入 PID、父子关系、`exec`（用新的 ELF 替换当前地址空间）、
以及 `waitpid` 和僵尸进程的回收。

到那时 `TaskControlBlock` 会再长大一圈，任务管理器也要从"一个定长任务表"
变成"一棵进程树"。
