# 第 14 章　阻塞与唤醒

> 对应 tag `v0.14`。本章代码：`git diff v0.13..v0.14`

## 14.1 这一章只做了一件事

表面上这章加了互斥锁、信号量、条件变量三样东西。但它们都只是外壳 ——
真正新增的只有一个能力：**让进程睡下，等事件来了再唤醒**。

前面几章留下的三笔账，根子全在这里：

| 欠账 | 当时的权宜之计 | 代价 |
|---|---|---|
| `waitpid`（第 9 章） | 返回 -2，让用户库循环重试 | 白烧时间片 + 多余的系统调用 |
| `Stdin::read`（第 10 章） | 没输入就 `yield` 重试 | 同上 |
| 串口丢字符（第 10 章） | 无解，只能在测试工具里绕 | **真的丢数据** |

轮询之所以"能用"，是因为调度器总会把 CPU 分给别人。但它有两个真实代价：
**浪费**（等待者反复被调度、什么也干不成）和**丢事件**
（没人盯着的那段时间里发生的事，没人知道）。

## 14.2 阻塞和让出的区别只有一行

```rust
pub fn suspend_current_and_run_next() {
    // ...标记 Ready...
    add_task(task);            // ← 放回就绪队列
    schedule(task_cx_ptr);
}

pub fn block_current_and_run_next() {
    // ...标记 Blocked...
    // 没有 add_task —— 这就是全部区别
    schedule(task_cx_ptr);
}
```

差别就在那一行。`Ready` 的进程调度器轮得到，`Blocked` 的进程
**调度器根本看不见** —— 它的 `Arc` 此刻只被某个等待队列握着。
只有别人显式 `wakeup_task` 把它放回去，它才会再跑。

这也说明了责任的转移：**等待者不再负责检查条件，唤醒者负责通知**。

## 14.3 先入队，再睡下

```rust
pub fn wait_on(queue: &WaitQueue) {
    queue.push(current_task());      // 先
    block_current_and_run_next();    // 后
}
```

这个顺序不能反。反过来的话，在"睡下"和"入队"之间事件就发生了，
唤醒者会发现队列是空的、于是什么都不做 —— 而我们随后睡下，
再也醒不过来。这就是经典的 **lost wakeup**。

本项目的内核不可抢占（第 5 章那个决定），所以这两步之间不会被打断，
把顺序摆对就够了。真正可抢占的内核还需要一把锁把两步包起来。

> `21condvar` 那个演示里留了一处**真实的竞态**并做了标注：
> 工头靠"`yield` 足够多次"来等工人们先睡下。这是错的写法 ——
> 正确做法是用一个共享状态位配合 `while` 循环。留着它是为了让
> lost wakeup 这件事有个具体的样子可看。

## 14.4 三个原语，一个底座

- **互斥锁**：一个 `bool` + 一个等待队列
- **信号量**：一个可以为负的计数 + 一个等待队列（负数的绝对值正是等待者个数）
- **条件变量**：一个等待队列，加上"放锁 → 睡下 → 重新上锁"的动作

它们的全部复杂度都在**边界条件**上，不在数据结构上。

### 为什么不用自旋锁

自旋锁等待时死死占着 CPU。在单核系统上这是最坏的选择 ——
持锁者根本没机会运行来释放锁，自旋只能一直转到时间片用完。

阻塞锁把等待者从调度器视野里拿掉，CPU 立刻给别人（很可能就是持锁者）。
代价是每次竞争多两次上下文切换。

规律：**争用少、临界区短**用自旋；**争用多、临界区长**用阻塞。
单核内核里几乎总该用阻塞。

### 醒来不等于拿到

```rust
pub fn lock(&self) {
    loop {
        if 抢到了 { return; }
        wait_on(&self.waiters);
        // 被唤醒之后要重新抢 —— 中间可能有别人插队
    }
}
```

这里是 `loop` 而不是 `if`。条件变量同理，所以所有条件变量的用法都要求
`while 条件不成立 { wait() }`。**唤醒只是"去看一眼"的信号，不是"归你了"的保证。**

## 14.5 一个踩到的坑：锁里不能放锁

第一次跑就 panic 了：

```
[KERNEL PANIC] src/sync/up.rs — RefCell already borrowed
```

原因在这一行：

```rust
notify_all(&parent.inner_exclusive_access().child_waiters);
```

`inner_exclusive_access()` 产生的 `RefMut` 活到整个语句结束，
而 `notify_all` 要去唤醒等待者 —— 等待者正是 `parent` 自己，
于是又借了一次同一个 `RefCell`。

修法不是调整语句顺序，而是**把等待队列从 `inner` 里搬出去**。
`WaitQueue` 本身就带内部可变性，压根不需要外层那道 `RefCell`。

> 教训：**能不放进锁里的东西就别放进去**，尤其是那些本身就是
> 同步设施的东西。它们迟早要在"持有外层锁"的情况下被使用。

## 14.6 死锁不能表现成"正常关机"

第 9–13 周，idle 控制流发现就绪队列空了就直接关机 —— 那时"队列空"确实
等于"活干完了"。

有了阻塞之后这个等式不成立了：队列可能空着，而一堆进程正互相等待。
如果还按老逻辑，**一次死锁会表现成系统正常退出**，这是最糟糕的失败方式：
出了大事，却什么都没说。

所以 idle 现在要分三种情况：

```text
  就绪队列空 ──┬── 有人在等 I/O  ──▶ 主动问一次 PLIC，然后 wfi 睡着等
               ├── 有人在互相等  ──▶ 报告死锁，以错误码关机
               └── 没人了        ──▶ 正常关机
```

`22deadlock` 就是用来验证它的：五位哲学家都先拿左手边的叉子，必然死锁。

```
  哲学家 0 拿到了左叉 0
  哲学家 1 拿到了左叉 1
  ...
[ERROR] 死锁：就绪队列已空，但还有 8 个进程阻塞在等待队列上
```

对照 `19philosophers`：唯一的区别是所有人都**先拿编号小的那只叉子**，
于是最后一位的顺序和别人相反，环就断了。输出里能直接看到：

```
  哲学家 4 第 0 轮：拿到叉子 0 和 4，开吃     ← 注意是 0 在前
  5 位哲学家都吃完了，没有人饿死。
```

## 14.7 把串口输入改成中断驱动

这是第 10 章那笔"真的丢数据"的账。

之前：内核靠 SBI 的 `console_getchar` 轮询。两次轮询之间到达的字符，
超出串口硬件那 16 字节 FIFO 就没了 —— 粘贴一段长命令会缺字母。

现在：内核直接驱动 16550 串口，打开接收中断。字符一到就产生中断，
内核在中断处理程序里把 FIFO **一次排空**，存进 256 字节的环形缓冲区，
并唤醒等着的进程。

```text
  字符到达 ──▶ UART 中断 ──▶ PLIC ──▶ 内核 ISR ──▶ 环形缓冲区 ──▶ 唤醒读者
```

处理外设中断的标准动作是**认领 + 完成**两步（`claim` / `complete`）。
少了第二步的后果很典型：中断只会来一次，之后设备再怎么叫都没反应。

还有一处容易漏：ISR 里必须 `while LSR 有数据 { 取 }` 把 FIFO 排空。
只取一个字符的话，剩下的不会再产生新中断（16550 是电平触发的），
系统就此失聪。

### idle 必须主动去问 PLIC

改完第一次测，提示符出来了但收不到输入。

原因是第 5 章那个决定：内核不可抢占，`sstatus.SIE = 0`。
所以中断在内核态只会**挂起**，不会被送达。

平时这不成问题 —— 内核很快就 `sret` 回用户态，挂起的中断立刻被处理。
但当**所有进程都阻塞**时，CPU 停在 idle 的 `wfi` 上，没有用户态可回，
挂起的中断就永远没人管。

所以 idle 要自己走一趟：

```rust
if io_blocked_count() > 0 {
    if poll_external() { continue; }   // 主动问 PLIC
    unsafe { asm!("wfi") };            // 确实没事就睡着等
}
```

`wfi` 负责"别空转烧 CPU"，主动轮询负责"别睡死"。两者缺一不可。

### 效果

一次性把六条命令灌进运行中的 shell（模拟粘贴）：

```
ccnuos> help
ccnuos> 18ls
ccnuos> 12words | 13upper | 14wc
ccnuos> 20semaphore
ccnuos> 19philosophers
ccnuos> exit
```

**一个字符都不丢**，环形缓冲区的丢弃计数是 0。

最能说明问题的是：`tools/capture.sh` 里那个"按行慢喂"的变通**删掉了**。
它本来就是为了绕过这个缺陷而存在的。

> **工具里的变通消失，本身就是内核真的修好了的证据。**

还剩一个边角：在**固件初始化串口之前**敲下的字符仍会丢。那发生在我们的
代码运行之前（OpenSBI 配置 UART 时会清 FIFO），真实机器上也一样 ——
BIOS 自检期间敲键盘同样没用。

## 14.8 这些锁是跨进程的，不是跨线程的

真实系统里互斥锁和条件变量是**进程内**的对象，用来同步同一地址空间里的
多个线程（pthread 那一套）。

CCNUOS 没有线程 —— 每个进程独占一个地址空间。所以这三样做成了
**系统级的内核对象**，用一个整数 ID 引用，更接近 System V 的信号量。
`fork` 之后子进程继承的是这个普通整数，于是指向同一把锁。

好处是哲学家就餐那种经典场景直接就能演；代价是没有"锁属于谁"的概念，
任何进程都能解开任何锁。**这是个有意的取舍，不是疏忽。**

另一条路是实现用户态线程（多个任务共享一个地址空间）。那需要把
`TaskControlBlock` 拆成"进程"和"线程"两层，是个不小的重构 ——
放在 16 周的最后阶段风险太大。
