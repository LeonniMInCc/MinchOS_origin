# 第 15 章　把内核里发生的事画出来

> 对应 tag `v0.15`。本章代码：`git diff v0.14..v0.15`
>
> 成果：`make trace` → [docs/trace.html](trace.html)

## 15.1 这一章要还的是第 1 周立的 flag

第 1 周定位这个项目时写了两条：**课程设计**（知识点完整、能交实验报告）
和**教学演示**（有文档、有可视化）。前十四周一直在还第一条，
第二条只兑现了文档。这一章补上可视化。

难点不在画图，在**取数**。内核跑在 QEMU 里，只有一根串口通向外界，
而且它自己就是被观测的对象 —— 没有外部的 profiler 可以依赖。

## 15.2 日志给人看，事件给程序看

前十四周一直在用 `info!`。它的输出是这样的：

```
[INFO ] 文件系统已挂载：根目录 26 个文件，inode 27 个，数据块 661/4096
```

自然语言、随手写、格式想改就改。**给人看的东西就该是这样**，
但它没法解析 —— 换个词，脚本就崩了。

所以这一章引入第二条输出通道，格式固定、字段明确：

```
@EV sched t=123456 pid=2
@EV sys   t=123460 pid=2 id=64
@EV area  t=123470 pid=2 vpn=0x10 pages=2 ppn=0x80a12 perm=R-XU
```

分工是死的：

> **内核只负责说清楚发生了什么，不负责说它长什么样。**

内核不知道甘特图的存在，脚本不知道 `TaskControlBlock` 长什么样。
两边只通过那一行文本耦合。好处很实在：这一章我把可视化推翻重写了三次，
内核一行都没动。

事件一共七种，加起来不到二十行代码：

| 事件 | 什么时候发 | 在哪 |
|---|---|---|
| `new` | 进程诞生 | `fork_current` / `add_initproc` |
| `sched` | 某进程拿到 CPU | `run_tasks` |
| `block` | 进程主动睡下 | `block_current_and_run_next` |
| `wake` | 进程被唤醒 | `wakeup_task` |
| `exit` | 进程退出 | `exit_current_and_run_next` |
| `sys` | 进入系统调用 | `syscall()` |
| `area` | 地址空间建好了 | `MemorySet::trace_layout` |

## 15.3 默认必须关掉，而且我能证明为什么

事件走串口，而串口极慢 —— 每个字符一次 SBI 调用。

这不是"有点开销"的问题。从事件自己的时间戳就能把成本量出来：
`area` 事件是在一个循环里连着打的，中间没有任何别的工作，
所以相邻两条的间隔**就是**打一条事件的代价。

```
每字符 3.92 µs（41 个样本）
本次事件共 23720 字符 → 约 93 ms 输出开销
同一次运行里 CPU 实际忙 153 ms
```

**这 153 ms 里有 61% 花在打印事件本身。**

也就是说，打开事件输出之后，内核用在"报告自己在干什么"上的时间，
比用在"干活"上的还多。调度行为已经被观测行为显著改变了 ——
教科书上的观测者效应，在这里是个可以测出来的数字。

所以它由编译期环境变量控制，和第 2 章的 `LOG` 同一个套路：

```rust
pub const ENABLED: bool = option_env!("TRACE").is_some();
```

`ENABLED` 是**编译期常量**，所有 `if ENABLED { ... }` 在关闭时整段被 LLVM 消除。
这一点验证过而不是想当然：

```
TRACE 关：镜像里 '@EV' 出现 0 次，.text 133644 字节
TRACE 开：镜像里 '@EV' 出现 1 次，.text 133606 字节
```

关闭时连那三个字符的记号都不在二进制里。至于 .text 反而小了 38 字节
（0.03%），那是内联决策的抖动，不值得解读 —— **结论是没有可测量的代价，
不是"变快了"**。

> 一个 Makefile 上的坑：`option_env!` 判的是"有没有设"，
> 所以 `TRACE=`（空值）也算打开。变量不能无脑往命令行上拼：
>
> ```makefile
> TRACE_ENV = $(if $(TRACE),TRACE=$(TRACE),)
> ```
>
> 另外 `os/build.rs` 里那行 `rerun-if-env-changed=TRACE` 是必需的。
> 少了它，改了 `TRACE` cargo 不会重新编译，于是你会拿一份没有事件的
> 旧内核去跑，然后对着空日志发呆。

## 15.4 串口是共享的，所以解析不能按行来

实际录出来的日志长这样：

```
[initproc] 我是 pid @EV sys t=61408 pid=0 id=64
0@EV sys t=61565 pid=0 id=64
，整个用户态世界从我开始。
```

用户程序的输出和事件挤在同一行上了。

但**事件本身是完整的**，从来没有被从中间切开。原因是第 5 章那个决定：
内核不可抢占。一条事件在内核态一口气打完，中途不会被切走。
交错只发生在不同的 `sys_write` 之间。

所以解析用正则**在整段文本里搜**，而不是按行切：

```python
EVENT_RE = re.compile(r"@EV (\w+) t=(\d+)((?: \w+=\S+)*)")
```

## 15.5 三个画错了的图

可视化最容易犯的错，是**画出来的东西看着挺像回事，但它是错的**。
这一章踩了三个，都值得记下来。

### 错误一：把空闲算在了阻塞的进程头上

第一版的甘特图上，pid 1 有一条 **2780 ms** 的运行区间。而时间片只有 10 ms。

原因是内核只在**被调度上来**时报告，从不报告"我交出了 CPU"。
天真的算法是"一个区间从 `sched` 画到下一个 `sched`"。可是进程阻塞之后，
如果没有别人就绪，CPU 会停在 idle 的 `wfi` 上 —— 这期间**一条 `sched` 都没有**。
那段空闲就被算进了上一个进程。

修法不是加事件，而是用已有的事件推：区间的结束时刻取两者中先到的那个 ——
下一次 `sched`，或者这个进程自己的 `block` / `exit`。
后两者恰好就是"它停止运行"的时刻。

改完之后最长区间变成 **10.655 ms**。那正好是一个时间片，
这个数字本身就是修对了的证据。

> 这里有个一般性的教训：**观测数据的缺口，往往不表现为"缺了一块"，
> 而表现为"某个值大得离谱"。** 画出来的图第一眼合理，恰恰最危险。

### 错误二：PID 不能当进程的身份

第二版的进程树里，`pid 2` 在同一层出现了两次，`pid 3` 也是。

不是 bug，是**真相**：`11forktest` 用完退出后，`19philosophers` 拿到了同一个号。
PID 是**当前存活进程**的唯一标识，不是进程历史的唯一标识。
我却拿它当了树的节点 ID。

修法是每个 `new` 事件建一个独立节点，父节点取"此刻还活着的、
pid 等于 ppid 的那个"。号码复用的地方现在显式标出来：

```
● pid 0 (initproc)　生于 0 ms　退出码 0
└─ ● pid 1　生于 5 ms　退出码 0
   ├─ ● pid 2　生于 1826 ms　退出码 0
   │  └─ ● pid 3　生于 1835 ms　退出码 42
   └─ ● pid 2　第 2 次用到这个号　生于 1857 ms　退出码 0
      ├─ ● pid 3　第 2 次用到这个号　生于 1866 ms　退出码 0
      ├─ ● pid 4　生于 1867 ms　退出码 0
      └─ ...
```

顺带印证了两件事：`11forktest` 的子进程退出码确实是 42；
`19philosophers` 的五位哲学家确实是同一个父进程连着 fork 出来的。

### 错误三：按真实比例画，等于什么都没画

一次交互式运行 2006 ms，其中 CPU 真正在忙的只有 **153 ms（7.6%）**，
剩下全在等人敲键盘。按真实比例画，所有活动会挤成一根看不见的竖线。

所以长于 15 ms 的空闲被折叠成固定宽度的斜纹条，**并在轴上标明折叠了多久**。
这是性能剖析工具的常规做法，关键在后半句：**压缩可以，但不能不说**。
时间刻度也只打在没被折叠的段上 —— 折叠段里时间不是线性的，标刻度就是骗人。

## 15.6 地址空间：一张图讲完分页

`area` 事件报的是**逻辑段**，不是页表。

SV39 的三级页表有 512×512×512 个槽位，整棵树倒出来既慢又没人看得下去。
而"段"恰好是人脑理解地址空间的粒度 —— 代码、只读数据、数据、栈，
一共四五条。每条附上首页的物理页号，于是这张表能同时讲清四件事：

```
● pid 3
0x0000000000010000  2p  R-XU  .text　代码      → ppn 0x805b2
0x0000000000012000  1p  R--U  .rodata　只读数据 → ppn 0x805a7
        guard page —— 不映射，栈写穿立刻缺页
0x0000000000014000  2p  RW-U  用户栈           → ppn 0x805a8
0xffffffffffffe000  1p  RW--  TrapContext      → ppn 0x805ac
```

1. **同一个程序在不同进程里，左边的虚拟地址完全一样，右边的物理页号完全不同。**
   这就是分页在做的事，一眼可见。
2. 没有任何一段同时带 `W` 和 `X`。
3. 最高那页不带 `U`，所以用户态碰不到 `TrapContext`。
4. 用户栈下面空着整一页，那就是 guard page。

> 一个解析上的坑：内核报的 `vpn` 是 SV39 的 27 位页号，
> `vpn << 12` 只有 39 位。SV39 要求高 25 位是第 38 位的**符号扩展**，
> 所以 `0x7fffffe` 对应的真实地址是 `0xffff_ffff_ffff_e000`。
> 不做这一步，跳板页和 TrapContext 会显示成两个莫名其妙的低地址。

表里看不到跳板页 —— 它不是一个 `MapArea`，而是被直接写进页表的，
所以内核根本没有为它报告 `area` 事件。**图上缺什么，也是信息。**

## 15.7 一个进程会报告好几次地址空间

`exec` 换掉整个地址空间，所以同一个 pid 会重报一轮。
shell 那个 pid 在一次运行里报了三代（`initproc` fork 出来的原样、
`exec` 成 `user_shell` 之后、再 `exec` 成别的程序之后）。

第一版把它们全拼进一张表，于是出现了自相矛盾的段。
修法是按"一串连续的 `area` 事件"分组，只留每个 pid 最后那一组 ——
连续性是可靠的，因为内核不可抢占，一轮报告中途不会插进别的事件。

## 15.8 怎么用

```bash
make trace          # 打开事件输出，录一次，生成 docs/trace.html
make run            # 默认关闭，零开销
```

喂给 shell 的命令在 `tools/trace-input.txt` 里，改它就能观测别的场景。
比如想看死锁长什么样，把 `19philosophers` 换成 `22deadlock`。

```
os/src/trace.rs              事件输出（新）
os/src/mm/memory_set.rs      + trace_layout()
os/src/task/{mod,tcb,processor}.rs   埋点
os/src/syscall/mod.rs        埋点
os/build.rs                  + rerun-if-env-changed=TRACE
tools/trace2html.py          宿主机渲染器（新）
tools/trace-input.txt        观测用的输入脚本（新）

```

内核侧一共不到 80 行。**可视化的复杂度几乎全在宿主机上，这是有意的** ——
内核里每多一行，就多一分在调试时干扰调度的可能。

## 15.10 练习

1. **给 `block` 事件加上原因**（等 I/O / 等子进程 / 等锁），
   在甘特图上用不同颜色的圈区分。想想这个信息内核手上有没有。
2. **统计上下文切换的类型**：区分"时间片用完被抢占"和"主动让出"。
   跑 `19philosophers` 看比例，再和第 5 章的时间片长度关联起来。
3. **把折叠阈值从 15 ms 改成 1 ms**，看图变成什么样。
   想清楚：阈值调小到什么程度，图就开始骗人了？
4. **加一个 `frame` 事件**，在页帧分配/回收时发出，
   画一张物理内存占用随时间变化的图。和第 9 章的泄漏检查对照。
5. **把 `sys` 事件改成进入和返回各发一次**，于是能画出每次系统调用的
   真实耗时。先估算一下：这会让事件量和开销变成多少倍？值不值？
6. **构造一个观测者效应**：写一个对时序敏感的用户程序，
   让它在 `TRACE=1` 和关闭时表现不同。这比任何解释都有说服力。
