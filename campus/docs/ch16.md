## 16.2 回归测试第一次跑就挂了一条

```
  通过  用户态与系统调用
  通过  协作式调度：三个任务交替
  ...
  通过  死锁必须被发现，而不是伪装成正常关机
  失败  持久化：重启后文件内容原样还在
          重启后读到的内容不是上次写的（时间戳 2485 对不上）

结果：14/15 通过，1 个失败
```

（那时还是 15 个用例。后来补上 `04spin_x` / `05spin_y` 那条，现在是 16 个，
覆盖全部 23 个演示程序。）

手工复现：

```
第一次启动：write: 往 readme.txt 写了 42 字节（时间戳 2433 ms）
第二次启动：cat: 共 0 字节
```

**文件在，内容没了。**

### 病因

块缓存是**写回**式的：`write` 只改内存里的副本并打上脏标记，
真正落盘发生在缓存项被淘汰的时候（`BlockCache::drop`）。
缓存有 16 项，演示用的工作量根本填不满，于是**一个块都没有写出去**。

而内核关机时从来没有调用过 `sync_all_blocks`。

### 为什么潜伏了四周

第 12 周开始，唯一证明"数据真的落盘了"的证据是启动计数器：

```
[INFO ] 持久化自检：这是第 5 次启动 —— 上次写进 bootcount 的内容确实留在磁盘上了
```

它是对的 —— 因为 `persistence_check` 恰好在写完之后自己调了一次
`sync_all_blocks`。那一行代码，把整个文件系统的持久化问题遮住了四周。

同时，所有演示看起来都正常：同一次运行里 `17write` 之后 `16cat` 读得到内容。
那是**缓存命中**，和磁盘一点关系都没有。

> **教训：「同一次运行里能读到」证明不了持久化。**
> 想验证落盘，测试就必须**跨越一次关机**。

### 修法

关机前同步，相当于 unmount：

```rust
fn sync_disk() {
    let n = easy_fs::sync_all_blocks();
    if n > 0 { info!("已将 {} 个脏块写回磁盘", n); }
}
```

死锁关机那条路径上也要同步 —— 死锁之前写进去的数据没有理由跟着一起丢。

**为什么不在 `close` 时就同步？** 那样每次关文件都要打一次磁盘，
写回缓存的意义就没了。真实系统也是这么做的：靠后台回写线程加上卸载时强制同步，
想立刻落盘的程序自己调 `fsync`。我们没有后台线程，关机就是唯一的卸载时刻。

### 顺手把契约钉死

`easy-fs` 这边一直是对的，错的是调用方。所以加的测试不是"sync 能不能工作"
（`重新挂载后数据还在` 早就验过了），而是**不 sync 的后果有多安静**：

```rust
#[test]
fn 不调用_sync_数据就只在内存里() {
    // ...写完之后，绕开缓存直接翻"磁盘"上的字节...
    assert!(!on_disk(text), "还没 sync，数据就已经落盘了 —— 那说明这不是写回缓存");

    let n = sync_all_blocks();
    assert!(n > 0, "有脏块没写回，sync_all_blocks 却报告 0");
    assert!(on_disk(text), "sync 之后数据仍然不在磁盘上");
    assert_eq!(sync_all_blocks(), 0, "重复 sync 不该再写盘");
}
```

没有报错、没有异常返回值，数据只是悄悄地不见了 —— 把这件事钉在测试里，
下次有人重构缓存时能看到代价。

> 这个 bug 是整个项目里最有说服力的一条：
> **人眼看了四周的演示都没看出来，脚本第一次跑就抓到了。**

## 16.3 回归测试怎么设计的

每个用例是"一串喂给 shell 的命令 + 两类断言"。

```toml
[[chapter.check]]
type = "run"
name = "拒绝用户传来的越界指针"
commands = ["07bad_syscall_arg"]
must     = ["被内核拒绝了"]
must_not = ["内核居然照做了"]
```

> **第 17 周更新**：这一周写的是 `tools/regress.py`，判据是一段 Python 列表。
> 接实验平台时它和判题器合并了 —— 判据搬进 `docs/checkpoints.toml`，
> 引擎搬进 `tools/checker.py`，`make regress` 变成"拿参考实现去判题"。
> 形式变了，下面讲的道理一个字没变。

### `must_not` 是更值钱的一半

那些"坏"程序里有这么一行：

```rust
println!("如果你看到这行，说明内核没拦住我 —— 那是个严重问题。");
```

这句话是第 3 到第 8 周陆续写下的，当时只是为了演示时看得清楚。
到这一周它们变成了现成的断言：**程序自己知道什么是失败，并且会把失败喊出来。**
测试只要盯着这句话有没有出现就行，完全不必理解它在干什么。

> 把失败条件写进**被测对象自己**，比写进测试脚本更不容易腐坏 ——
> 程序改了，那句话会跟着一起改；写在外面的断言则会悄悄地失去意义。

### 三条全局断言

对每一次启动都成立（死锁用例除外）：

1. 不出现 `[KERNEL PANIC]`
2. 出现"无泄漏"——整条 RAII 链的端到端检验
3. 不出现"串口输入缓冲区溢出"

第 2 条尤其划算：它不针对任何具体功能，但**任何一个忘了归还资源的改动
都会让它报警**。十五周攒下来的这条检查，在这里变成了所有用例共享的安全网。

### 为什么分成 16 次启动

因为 `exit` 会关机。分组还有个好处：一组挂了，其他组的结果仍然有效 ——
不至于一个失败就什么信息都拿不到。

代价是慢（约 2 分钟）。但它一天跑不了几次，没必要为此牺牲隔离性。

## 16.4 顺手修的两处

### README 里有一句不真的话

README 一直写着"代码里的 `unsafe` 块都附了说明"。这周去核对了一下：

```
unsafe 块 51 个，其中 11 个附近没有 SAFETY 说明
```

这是个**overclaim**。两条路：改 README，或者把它变成真的。选了后者，
11 处都补上了。现在：

```
unsafe 块 51 个，缺 SAFETY 说明的 0 个
```

> 交付物里一句不准确的话，和代码里的一个 bug 是同一类东西。
> 区别只在于前者更容易被原谅，所以更容易一直留着。

### 版本号有两个来源

`Cargo.toml` 停在 `0.12.0`，而启动横幅已经写到 `v0.15.0`——
因为它是硬编码的。改成 `env!("CARGO_PKG_VERSION")`，从此只有一个来源。

## 16.6 十六周下来，三件做对的和三件没做够的

### 做对的

1. **每周一个能跑的版本。** 从第 1 周起就能 `make run` 看到东西。
   没有"写三周再第一次运行"这种事，所以每个 bug 的引入点都在一周之内。
2. **文件系统独立成 crate。** 只依赖一个 `BlockDevice` trait，
   于是能在宿主机上秒级测试。全项目回报率最高的一个决定 ——
   文件系统的调试基本没进过 QEMU。
3. **把坑写下来。** 实验报告里最有价值的第四节，全部来自当周的文档。
   当时只花了十几分钟写，四个月后价值翻了很多倍。

### 没做够的

1. **回归测试来得太晚。** 它第一次跑就抓到一个潜伏四周的数据丢失 bug。
   如果第 10 周就有，这个 bug 活不过一周。
   > **测试基础设施的价值，与引入时间成反比。**
2. **可视化可以更早。** 第 15 周做出来之后才发现，一张甘特图对理解调度的
   帮助远超读代码。
3. **性能没有系统测量过。** 只在需要证明某个结论时才测
   （第 5 周的时间片、第 15 周的观测开销）。没有基线，就说不出
   "这个改动让上下文切换快了多少"。

## 16.7 如果还有第 17 周

按投入产出排序：

1. **写时复制。** `fork` 现在整体拷贝地址空间。COW 能把它变成几乎零成本，
   而且是理解"页错误不只是错误"的最好例子。
2. **用户态线程。** 把 `TaskControlBlock` 拆成进程和线程两层，
   同步原语就能从系统级回到进程内，更接近真实系统。
3. **`lseek` / `unlink` / 子目录。** 文件系统还缺这三样才算完整。
4. **把回归测试接进 CI。** 现在要手工跑。

## 16.8 练习

1. **给回归测试加一个用例**，验证你认为最可能坏掉的那个功能。
   想清楚它的 `must_not` 是什么 —— 这比 `must` 难。
2. **故意破坏一处代码**（比如把 `FrameTracker` 的 `Drop` 注释掉），
   看回归测试第几条先报警。如果一条都不报，那说明覆盖有洞。
3. **把关机时的 `sync_disk` 去掉**，跑回归测试，确认那一条确实会红。
   一条从来不会失败的测试没有价值。
4. **量一量 `fork` 的成本**：在 `11forktest` 里加计时，
   再估算写时复制能省下多少。这是第 17 周第一件事的可行性论证。
5. **读一遍 `git log --oneline`**，找出你觉得最该被拆成两个 commit 的那一个。
