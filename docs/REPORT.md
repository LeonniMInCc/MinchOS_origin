# CCNUOS 实验报告

> 一个用 Rust 从零编写的 RISC-V 教学操作系统
>
> 版本 `v1.0` · 16 周 · 单人完成

---

## 一、项目概述

CCNUOS 是一个运行在 QEMU `virt` 机器上的 RISC-V 64 位操作系统内核，
用 Rust（stable，`no_std`）从零编写，**不依赖任何第三方 crate**。

它能做到：从上电开始接管机器，建立虚拟内存，把程序从自己的文件系统里
读出来、装进各自独立的地址空间去执行，在它们之间抢占式地分配 CPU，
让它们通过管道和同步原语协作，并且在它们越权时拦住它们。

最终形态是一个可交互的 shell：

```
ccnuos> 12words | 13upper | 14wc
ccnuos> 12words > out.txt
ccnuos> 19philosophers
```

### 关键指标

| 项目 | 数值 |
|---|---|
| 内核代码 | 约 4200 行（另有 2700 行注释） |
| 文件系统 | 约 1160 行（独立 crate，宿主机可测） |
| 用户程序 | 25 个（23 个演示程序 + initproc + shell），约 1100 行 |
| 宿主机工具 | 约 940 行（Python / Shell） |
| 讲解文档 | 16 章，约 4200 行 |
| 系统调用 | 24 个 |
| 外部依赖 | **0** |
| `unsafe` 块 | 51 个，**每一个都附有 SAFETY 说明** |
| 单元测试 | 18 个（宿主机，0.01 s） |
| 回归测试 | 16 个用例，覆盖全部 23 个演示程序（QEMU 端到端） |

### 技术选型

| 选择 | 理由 |
|---|---|
| RISC-V | 特权级规范简洁完整，没有 x86 的历史包袱；手册读得完 |
| Rust stable | 所有权模型能把"资源必须归还"变成编译期约束；不用 nightly 是为了工具链不会某天早上自己坏掉 |
| QEMU virt | 无需硬件，可脚本化，可 GDB 单步 |
| 零外部依赖 | `sbi-rt`、`log`、`bitflags` 省下的那点代码量，远不如亲眼看见 `ecall` 怎么发生值钱 |

## 二、系统架构

```text
┌──────────────────────────────────────────────────────┐
│  用户态 (U)   initproc → user_shell → 23 个演示程序      │
│               每个进程一个独立地址空间                    │
└───────────────────────┬──────────────────────────────┘
                        │ ecall (24 个系统调用)
┌───────────────────────▼──────────────────────────────┐
│  内核态 (S)                                            │
│  ┌─────────┬─────────┬─────────┬─────────┬─────────┐  │
│  │  trap   │  task   │   mm    │   fs    │  sync   │  │
│  │ 陷入分发 │ 进程调度 │ 地址空间 │ 文件抽象 │ 阻塞唤醒 │  │
│  └─────────┴─────────┴────┬────┴────┬────┴─────────┘  │
│                  drivers  │ easy-fs │                 │
│              virtio-blk / PLIC / UART                 │
└───────────────────────┬──────────────────────────────┘
                        │ ecall (SBI)
┌───────────────────────▼──────────────────────────────┐
│  机器态 (M)   OpenSBI —— 串口、时钟、关机                │
└──────────────────────────────────────────────────────┘
```

### 各模块职责

| 模块 | 职责 | 核心抽象 |
|---|---|---|
| `mm` | 物理页帧、内核堆、SV39 页表、地址空间 | `FrameTracker`（RAII）、`MemorySet`、`MapArea` |
| `trap` | 特权级切换、异常与中断分发 | `TrapContext`（34 个寄存器）、跳板页 |
| `task` | 进程生命周期、调度、上下文切换 | `TaskControlBlock`、`TaskContext`（14 个寄存器） |
| `fs` | 文件抽象 | `File` trait —— 标准流 / 管道 / 磁盘文件共用一组动词 |
| `sync` | 阻塞与唤醒 | `WaitQueue`，其上建互斥锁 / 信号量 / 条件变量 |
| `drivers` | 设备 | virtio-blk（virtqueue）、PLIC、16550 串口 |
| `easy-fs` | 文件系统本体 | `BlockDevice` trait —— 与外界唯一的接口 |

## 三、关键设计决策

这一节只写那些**当时可以选另一条路**的地方。没有取舍的实现细节不在此列。

### 3.1 用 RAII 管理内核资源

物理页帧、PID、内核栈、打开的文件、脏的缓存块 —— 全部由 `Drop` 负责归还。

这不是风格问题。传统内核里"分配后忘了释放"是最常见的一类 bug，
而且症状（几小时后内存耗尽）离病因（某个错误分支提前 return）极远。
把归还绑在类型的析构上之后，**这类 bug 在编译期就不可能写出来**。

验证方式是端到端的：内核在关机前核对页帧数量与用户态启动前是否一致。

```
[INFO ] 页帧核对：72 页，与用户态启动前完全一致，无泄漏
```

这一条检查在第 9 周救过一次场：它报告泄漏 7 页，查下来是 `INITPROC`
静态变量仍持有 PCB —— 不是真泄漏，但说明这条检查确实在工作。

### 3.2 内核不可抢占（`sstatus.SIE = 0`）

进入内核态后关中断，直到 `sret` 返回用户态。

**代价**：内核里的长操作会推迟中断响应。
**收益**：内核中的任意一段代码都不会被打断，于是
- `UPSafeCell`（`RefCell` + `unsafe Sync`）是成立的；
- "先入队、再睡下"两步之间不会插进别人，不需要额外的锁；
- 一条事件日志不会被打印到一半。

这是单核教学系统上的正确取舍，多核下会立刻失效 —— 文档里明确写了这一点，
而不是留给读者去踩。

### 3.3 `UPSafeCell` 用 `RefCell` 而不是 `UnsafeCell`

后者更快，前者在违反"同时只有一个可变借用"时会**当场 panic**。

教学系统要的就是这个：错误要响，不要静。这个选择在第 10 周和第 14 周
各抓到一次真实的双重借用（见 3.6）。

### 3.4 `File` trait：一组动词，三种实现

```rust
trait File { fn readable/writable/read/write }
```

标准输入输出、管道、磁盘文件都实现它。于是 shell 的重定向和管道
不需要知道 fd 背后是什么东西 —— Unix "一切皆文件" 的收益在这里是具体的：
`12words | 13upper > out.txt` 这条命令能工作，没有为它写过一行特判。

### 3.5 easy-fs 做成独立 crate

它只依赖一个 `BlockDevice` trait，不依赖内核的任何东西。因此：

- 在宿主机上用一段内存模拟块设备，`cargo test` **0.01 秒**跑完 18 个测试；
- 制作磁盘镜像的工具 `easy-fs-fuse` 和内核**共用同一份代码**，
  从根本上杜绝了"制作工具和内核对磁盘布局理解不一致"这类 bug。

这个决定的回报是整个项目里最高的：文件系统的调试基本没有进过 QEMU。

### 3.6 同步原语是系统级的，不是进程内的

真实系统里互斥锁和条件变量是进程内对象，同步同一地址空间的多个线程。
CCNUOS 没有线程，所以这三样做成了用整数 ID 引用的**内核对象**，
更接近 System V 信号量。

好处是哲学家就餐那种跨进程场景直接能演；代价是没有"锁属于谁"的概念。
**这是有意的取舍**：另一条路是实现用户态线程，需要把 `TaskControlBlock`
拆成进程和线程两层，在第 14 周引入风险过大。

## 四、踩过的坑

工程价值最高的部分。这里只选那些**改变了我对系统的理解**的。

### 4.1 DMA 到内核栈，读出来全是 0（第 13 周）

**现象**：从磁盘读块，启动期间一切正常，进程运行起来之后读到的全是 0。

**原因**：`BlockCache::new` 把一个栈上的 `[u8; 512]` 的地址交给设备当物理地址。
启动期间栈在 `.bss` 里，而 `.bss` 是恒等映射的，所以"虚拟地址 = 物理地址"
恰好成立。但第 8 周之后**内核栈改成了 `Framed` 映射在高地址**，
这个等式不再成立，设备被指向了一片无关的物理内存。

**修法**：用一个静态的弹跳缓冲区（bounce buffer）。

**更重要的后续**：第 12 章的文档里写过一句"任何内核指针的数值本身就是物理地址"。
这句话在当时是对的，在第 13 周变成了错的。我回去给它加了一个警示框并指向本章。

> **教训**：设备看到的地址空间和 CPU 看到的不是一回事。
> 恒等映射会让这个区别暂时消失，然后在某个不相干的改动之后突然回来。

### 4.2 关机不落盘，文件系统静默丢数据（第 16 周发现，潜伏 4 周）

**现象**：回归测试第一次跑就挂了一条 —— 写 42 字节，重启后读到 0 字节。

**原因**：块缓存是写回式的，真正落盘发生在缓存项被淘汰时。
缓存没满就一个块都不会写出去。而内核**关机时从来没有调用过 `sync_all_blocks`**。

那为什么四周都没发现？因为唯一证明"落盘了"的证据是启动计数器，
而它恰好在写完之后自己同步了一次。用户程序写的文件从未真正持久化，
但同一次运行里读当然读得到（缓存命中），所有演示都"正常"。

**修法**：关机前同步，相当于 unmount。同时在 easy-fs 里加了一个测试，
钉死"不调 sync 就不落盘"这条契约。

> **教训**：**"同一次运行里能读到"证明不了持久化。**
> 想验证落盘，测试就必须跨越一次关机。
>
> 这个 bug 是整个项目里最有说服力的一条：它证明了自动化回归测试的价值 ——
> 人眼看了四周的演示都没看出来，脚本第一次跑就抓到了。

### 4.3 `__alltraps` 破坏了犯罪现场（第 7 周）

**现象**：内核自己出错时，报告的 `stval` 是一个荒谬的值。

**原因**：`__alltraps` 开头无条件 `csrrw sp, sscratch, sp` 交换栈指针。
这个动作只对"从用户态陷入"有意义。内核态出错时 `sscratch` 是 0，
于是 `sp` 被换成 0，后续保存上下文的操作把现场彻底毁掉。

**修法**：给内核态单独一个入口 `__kernel_trap`，不换栈。
`stvec` 在 `__restore` 开头切回 `__alltraps` —— 选这个位置是因为
它覆盖**所有**进入用户态的路径，不会漏。

> **教训**：错误处理路径本身出错，比原始错误难查一个数量级。

### 4.4 错误日志里的整数溢出（第 3 周）

```rust
error!("非法缓冲区 [{:#x},{:#x})", buf, buf + len);
```

用户传一个巨大的 `len` 时，`buf + len` 溢出。release 下悄悄回绕成一个
看起来正常的小地址，debug 下直接 panic —— **在处理恶意输入的代码里 panic**。

**修法**：分别打印 `ptr` 和 `len`，不做算术。

> **教训**：错误处理路径也在信任边界上。校验代码本身必须能承受被校验的输入。

### 4.5 持有锁时调用可能让出 CPU 的函数（第 10、14 周，两次）

第 10 周：握着 PCB 的借用去调 `file.read()`，而它可能阻塞。
第 14 周：`notify_all(&parent.inner_exclusive_access().child_waiters)` ——
临时的 `RefMut` 活到语句结束，而 `notify_all` 要唤醒的正是 `parent` 自己。

两次都当场 panic（这正是 3.3 那个决定的回报）。

第二次的修法不是调整语句顺序，而是把等待队列**从锁里搬出去**：
`WaitQueue` 本身就有内部可变性，不需要外层那道 `RefCell`。

> **教训**：**能不放进锁里的东西就别放进去**，尤其是同步设施本身 ——
> 它们迟早会在"持有外层锁"的情况下被使用。

### 4.6 cargo 不把链接脚本当作构建输入（第 6、8 周，复发一次）

改了链接脚本里的基地址，cargo 认为什么都没变，复用旧产物。
第一次的修法（删除输出文件强制重链）是错的 —— cargo 只是从 `deps/`
重新拷贝一份。

**最终修法**是两道：`build.rs` 里声明 `rerun-if-changed=src/linker.ld`，
**加上** Makefile 构建后逐个核对 ELF 的入口地址，对不上就报错并提示
`make clean-user`。

> **教训**：构建系统的缓存假设一旦不成立，症状会表现在离它极远的地方
> （程序跑飞）。防线要设在离病因最近处，而且要**主动核对**，不能只靠声明。

### 4.7 观测行为改变了被观测的对象（第 15 周）

事件输出走串口，每字符一次 SBI 调用。从事件自身的时间戳量出来：

```
每字符 3.92 µs → 本次 23720 字符 ≈ 93 ms 输出开销
同一次运行 CPU 实际忙 153 ms
```

**61% 的 CPU 时间花在打印"CPU 在干什么"上。**

所以事件输出由编译期常量控制，关闭时 LLVM 整段消除 ——
验证过：关闭时二进制里连 `@EV` 这三个字符都不存在。

## 五、测试与验证

三层，各管一段，反馈速度相差三个数量级。

| 层次 | 范围 | 工具 | 耗时 |
|---|---|---|---|
| 单元测试 | easy-fs 内部逻辑 | `make test`（宿主机） | 0.01 s |
| 内核自检 | 堆 / 页帧 / 页表 / 地址空间 | 每次启动自动跑 | 启动时 |
| 回归测试 | 23 个演示程序端到端 | `make regress`（QEMU） | 约 2 min |

### 回归测试的设计

每个用例是"一串喂给 shell 的命令 + 对输出的断言"，断言分两类：

- **must**：必须出现的字符串
- **must_not**：绝不能出现的字符串

`must_not` 是更值钱的一半。那些"坏"程序自己知道什么是失败：

```rust
println!("如果你看到这行，说明内核没拦住我 —— 那是个严重问题。");
```

测试只要盯着这句话有没有出现就行，不必理解它在干什么。
**把失败条件写进被测对象自己**，比写进测试脚本更不容易腐坏。

另有三条全局断言，对每一次启动都成立：不出现 `[KERNEL PANIC]`、
出现"无泄漏"、不出现"串口输入缓冲区溢出"。

### 当前结果

```
结果：16/16 通过
```

覆盖：用户态与系统调用、协作式与抢占式调度、四类越权拦截、fork 地址空间隔离、
管道与三级流水线、文件读写与重定向、三种同步原语、死锁检测、跨重启持久化。

### 不靠断言而靠实测的几处

| 结论 | 怎么证明的 |
|---|---|
| 时间片轮转真的在工作 | 两个纯计算程序并发时墙钟时间正好翻倍 |
| 栈写穿会被拦住 | 故意越过 guard page 写，观察缺页异常 |
| 数据真的落盘了 | 连开三次，启动计数器递增 |
| 串口输入不再丢字符 | 一次性灌入六条命令，丢弃计数为 0 |
| 事件输出零开销 | 对比二进制里 `@EV` 的存在性与 `.text` 大小 |

## 六、明确没做的事

在 192 小时预算下放弃，且每一条都在文档里写明了原因：

| 没做 | 原因 |
|---|---|
| SMP 多核 | 需要重做全部同步原语，40 h 起步 |
| 写时复制 | `fork` 直接整体拷贝，逻辑清楚；COW 是独立话题 |
| 用户态线程 | 需把 TCB 拆成进程/线程两层，第 14 周引入风险过大 |
| 网络协议栈 | 与操作系统核心概念关系不大 |
| 真实硬件移植 | 调试成本高，收益主要在设备驱动 |

以及一批有意的简化，都写在对应章节里：块缓存不按设备号索引、
`sys_listdir` 不是 POSIX `getdents`、没有 `lseek` / `unlink` / 子目录、
管道断开不产生 SIGPIPE、固件初始化串口之前敲的字符仍会丢。

> 把简化写出来，和把它藏起来，是两种完全不同的工程态度。
> 一个教学系统尤其不该让读者误以为某个简化是"正确实现"。

每周一个 tag、一篇文档。`git diff v0.7..v0.8` 就是第 8 章的全部代码，
**代码的演进史本身就是教学材料** —— 这是第 1 周定下的结构，坚持了十六周。

### 做对的三件事

1. **每周一个可运行的版本。** 从第 1 周起就能 `make run` 看到东西。
   没有"写三周再第一次运行"这种事，所以每个 bug 的引入点都在一周之内。
2. **文件系统独立成 crate。** 秒级反馈，全项目回报率最高的一个决定。
3. **把坑写下来。** 这份报告里最有价值的第四节，全部来自当周的文档。

### 做得不够的

1. **回归测试来得太晚。** 它在第 16 周第一次跑就抓到一个潜伏四周的
   数据丢失 bug。如果第 10 周就有，这个 bug 活不过一周。
   **测试基础设施的价值与引入时间成反比。**
2. **可视化可以更早。** 第 15 周做出来之后才发现，甘特图对理解调度的
   帮助远超读代码。
3. **性能没有系统测量过。** 只在需要证明某个结论时才测。

## 八、怎么复现

```bash
brew install rustup qemu
rustup default stable
rustup target add riscv64gc-unknown-none-elf
```
