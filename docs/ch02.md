# 第 2 章　内核堆：让 `Vec` 能用

> 对应 tag `v0.2`。本章代码：`git diff v0.1..v0.2`

## 2.1 这一章要解决的问题

第 1 章结束时，内核能打印、能关机，但**不能保存任何数量不定的东西**。

想记录"当前有哪些进程"？进程数是变的，需要 `Vec`。
想做页表？页表项数组大小取决于映射了多少页。
想要文件描述符表？同理。

这些全都需要**动态内存分配**。而裸机上没有 `malloc` —— 这一章就是把它造出来。

Rust 把这件事切得很干净：`alloc` crate 提供 `Box`/`Vec`/`String`/`BTreeMap`，
它不假定操作系统存在，只要求你提供一个 `#[global_allocator]`。
我们提供了，整套容器就活了。

## 2.2 为什么选伙伴系统

内核需要的分配器要满足两点：能反复分配释放任意大小，且**不会随时间推移
碎片化到不可用**。

伙伴系统 (buddy system) 用一条极简规则做到这点：**所有块大小都是 2 的幂，
一个块只能和它唯一的"伙伴"合并**。

而伙伴的地址有个漂亮性质 —— 把自己地址的第 `k` 位翻转，就是伙伴的地址：

```text
块大小 2^4 = 16 字节

  0x1230 ^ 0x10 = 0x1220   ← 0x1230 的伙伴
  0x1240 ^ 0x10 = 0x1250   ← 0x1240 的伙伴
```

注意 `0x1230` 的伙伴是 `0x1220` 而**不是**紧邻的 `0x1240`。伙伴关系由地址
的二进制结构决定，不是简单的"左右相邻"。正因如此，一次异或就能算出伙伴在哪，
分配器完全不需要为"谁和谁能合并"做任何记账。

代价是**内部碎片**：申请 33 字节会实打实占掉 64 字节。运行日志里能直接看到：

```
[DEBUG] 申请 33 字节 → 实际占用 64 字节（伙伴系统只认 2 的幂）
```

对内核元数据这种"小对象、生命周期长短不一、但总量可控"的分配模式，这个代价划算。

## 2.3 侵入式空闲链表

分配器自己也要存数据 —— `free_list[k]` 是所有大小为 `2^k` 的空闲块组成的链表。
但链表节点存哪儿？如果另外开一块内存存节点，那这块内存又由谁来分配？

答案是**存在空闲块自己的内存里**：

```rust
unsafe fn push(&mut self, block: *mut usize) {
    *block = self.head as usize;   // 借用空闲块开头 8 字节存 next 指针
    self.head = block;
}
```

空闲块反正没人在用，借它开头的 8 个字节存链表指针，分配器本身就**零元数据开销**。
这也解释了 `block_size` 里那个看似奇怪的下界：

```rust
max(layout.size().next_power_of_two(),
    max(layout.align(), size_of::<usize>()))
//                      ^^^^^^^^^^^^^^^^^^ 至少要放得下一个 next 指针
```

`remove()` 用了一个值得学的技巧 —— 遍历时持有的是**指向 next 槽位的指针**
（`*mut *mut usize`）而不是节点本身：

```rust
let mut slot: *mut *mut usize = &mut self.head;
while !(*slot).is_null() {
    let block = *slot;
    if block == target {
        *slot = *block as *mut usize;   // 摘除，头节点无需特殊处理
        return true;
    }
    slot = block as *mut *mut usize;
}
```

因为 `head` 本身就是一个"next 槽位"，删除头节点和删除中间节点就变成了同一段代码。

## 2.4 分配与释放

**分配**：从需要的 class 往上找第一个非空链表，然后自顶向下对半劈，
每劈一次两个半块互为伙伴，都挂进下一级：

```
需要 64 B (class 6)，但只有一个 4096 B (class 12) 的块

 4096 ──┬── 2048  ← 挂进 free_list[11]
        └── 2048 ──┬── 1024  ← 挂进 free_list[10]
                   └── 1024 ──┬── ...
                              └── 64   ← 拿走
```

**释放**：挂回去，然后只要伙伴也空闲就合并，一路往上：

```rust
while class + 1 < MAX_ORDER {
    let buddy = block ^ (1usize << class);
    if self.free_list[class].remove(buddy as *mut usize) {
        block = min(block, buddy);   // 合并后的块从较低地址开始
        class += 1;
    } else {
        break;
    }
}
```

`remove` 返回 `true` 既表示"伙伴是空闲的"，又顺手把它摘下来了 —— 一个函数
同时完成判断和操作，这正是伙伴系统实现紧凑的原因。

## 2.5 `UPSafeCell`：把 unsafe 记成账

Rust 要求 `static` 必须是 `Sync` 的，而分配器需要可变。这里引入了一个
后面会反复用到的模式（见 [`sync.rs`](../os/src/sync.rs)）：

```rust
pub struct UPSafeCell<T> { inner: RefCell<T> }
unsafe impl<T> Sync for UPSafeCell<T> {}
```

关键是**用 `RefCell` 而不是裸 `UnsafeCell`**。我们完全可以用后者绕过所有检查，
但那样一来违反不变量时得到的是一段诡异的内存损坏；用 `RefCell` 得到的是一个
有文件名和行号的 panic。

这个 `unsafe impl Sync` 依赖一条我们必须自己维护的不变量：**单核，且访问期间
不被抢占**。这条不变量**会在第 5 周开启时钟中断后变弱** —— 中断处理程序可能
在临界区中间插进来。到时候要升级成"访问期间关中断"。

现在把这笔账记在类型文档里。内核里每一个 `unsafe` 都应该这样对应一条
写下来的不变量，否则三个月后没人知道它凭什么是对的。

## 2.6 一个值得追究的现象

运行日志：

```
[INFO ] 内核堆就绪：[0x0080217000, 0x0080517000)  3072 KiB
[DEBUG] Box<u32>      @ 0x0080516000    ← 堆的高端
[DEBUG] Vec<usize>×500 @ 0x0080217000    ← 堆的低端
```

为什么先分配的 `Box` 跑到高端，后分配的 `Vec` 反而在低端？

因为 `add_to_heap` 把这 3 MiB **切成了大小不一的块**。伙伴系统要求大小为
`2^k` 的块必须 `2^k` 对齐，而堆起点 `0x80217000` 只能 4 KiB 对齐，所以只能
先切一个小块，地址越往后对齐能力越强、块越大，到末尾又变小：

```
0x80217000  4 KiB   ← 受起点对齐限制
0x80218000  32 KiB
0x80220000  128 KiB
0x80240000  256 KiB
...
0x80500000  64 KiB
0x80510000  16 KiB
0x80514000  8 KiB
0x80516000  4 KiB   ← 受剩余空间限制
```

`free_list[12]`（4 KiB 那一级）里有两个块，而 `push` 是往链表头插的，
所以 `pop` 先拿到**后加入**的 `0x80516000`。于是：

1. `tiny`（64 B）从 `0x80516000` 劈出来，释放后完整合并回去
2. `Box`（8 B）又从 `0x80516000` 劈 —— 它是链表头
3. `Vec` 最终扩容到 4096 B，此时 `0x80516000` 那块正被 `Box` 占着，
   于是拿到了链表里的另一个 4 KiB 块 `0x80217000`

**结论**：分配器行为完全确定，只是"确定"不等于"符合直觉"。
内核调试中大量时间花在这类地方 —— 看到意外结果时，先假设自己的心智模型错了，
而不是假设代码错了。

## 2.7 开机自检代替单元测试

内核跑不了 `cargo test`（测试框架依赖 std），所以正确性验证做成了开机自检。
[`heap_test()`](../os/src/mm/heap_allocator.rs) 验证三件事：

1. 分配到的地址确实落在我们划的堆范围内
2. `Box` / `Vec` / `String` / `BTreeMap` 都能正常工作
3. **全部释放后用量精确回到基线** —— 这条最重要，它能抓住合并逻辑的错误

```
[INFO ] 堆自检通过：容量 3072 KiB，峰值占用 6680 B，释放后回落至 0 B
```

那个 `回落至 0 B` 是整个自检的价值所在：如果 `dealloc` 的伙伴合并写错了，
块会以碎片形式滞留，这个数字就不会归零。

## 2.8 内存布局的变化

```diff
- .bss             [0x0080213000, 0x0080213000)        0 B  (   0 KiB)
+ .bss             [0x0080217000, 0x0080518000)  3149824 B  (3076 KiB)
- kernel total     [0x0080200000, 0x0080213000)  共 76 KiB
+ kernel total     [0x0080200000, 0x0080518000)  共 3168 KiB
```

内核从 76 KiB 涨到 3168 KiB，几乎全是堆。这提醒一件事：**`KERNEL_HEAP_SIZE`
是实打实的物理内存开销**，不是"按需增长"的。第 6 周做页帧分配器时，
`ekernel`（现在是 `0x80518000`）之后的物理内存才是可以分给用户进程的部分。

## 2.9 练习

1. **把 `KERNEL_HEAP_SIZE` 改成 `0x1000`（4 KiB）**，然后在自检里分配一个
   大 `Vec`。观察 OOM 时发生了什么 —— 你会看到 `alloc` 返回空指针后，
   Rust 默认的 alloc error handler 触发 panic，最终走到我们第 1 章写的
   panic handler。整条链路是通的。
2. **故意写错合并逻辑**：把 `dealloc` 里的 `block = min(block, buddy)` 改成
   `block = buddy`，看自检的"回落至 0 B"如何抓住它。
3. **打印空闲链表分布**：写一个 `dump_free_lists()`，把每一级有几个空闲块
   打出来，验证 2.6 节推演的那张切分表。
4. **想一想**：如果把 `add_to_heap` 的起始地址强行对齐到 2 MiB，切分结果会
   变成什么样？分配行为会更符合直觉吗？
