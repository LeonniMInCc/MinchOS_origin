# 第 3 章　特权级切换：让代码跑在用户态

> 对应 tag `v0.3`。本章代码：`git diff v0.2..v0.3`
>
> 这是整个项目的第一个坎。前两章内核都是在自言自语，从这一章起，
> 它开始真正扮演"操作系统"的角色：管理别的程序。

## 3.1 这一章要解决的问题

到目前为止，CCNUOS 里只有一个执行流 —— 内核自己。这一章要造出第二个：
**一段不受信任的代码，跑在受限的特权级上，只能通过内核规定的方式请求服务。**

这需要回答三个问题：

1. 怎么让一段代码跑在 U 态？
2. 它想干点什么（比如打印）时，怎么把控制权交给内核？
3. 内核处理完，怎么让它接着往下跑，像什么都没发生过？

## 3.2 RISC-V 的三个特权级

```text
  M 态 (Machine)     ← OpenSBI 固件跑在这里，能碰所有硬件
      │ ecall
  S 态 (Supervisor)  ← CCNUOS 内核跑在这里
      │ ecall              ↑ sret
  U 态 (User)        ← 用户程序跑在这里，什么特权都没有
```

每一层只认识自己下面那一层。用户程序想打印，得 `ecall` 求内核；
内核想打印，得 `ecall` 求 SBI。**第 1 章写的 `sbi.rs` 和这一章写的
`user/src/syscall.rs`，是同一个模式在不同层的两次实现。**

## 3.3 核心洞察：启动程序 = 从一次不存在的 trap 返回

这是本章最值得记住的一件事。

一开始你可能会想："我需要写一段代码，把 CPU 切到 U 态，设好栈，跳到程序入口。"
但 RISC-V 已经有一条指令干这件事了 —— `sret`，它本来的用途是"处理完 trap 返回用户态"。

`sret` 做的事是：

- 根据 `sstatus.SPP` 决定返回到哪个特权级
- 跳转到 `sepc` 指向的地址

那么，要让一个程序从 `entry` 开始在 U 态运行，只需要**伪造一份现场**：

```rust
pub fn app_init_context(entry: usize, sp: usize) -> Self {
    let mut sstatus = sstatus::read();
    sstatus &= !sstatus_bits::SPP;   // SPP = 0 → sret 回到 U 态
    let mut cx = Self { x: [0; 32], sstatus, sepc: entry };
    cx.set_sp(sp);
    cx
}
```

然后走正常的 `__restore` 返回路径。**我们不需要为"启动程序"单独写一行汇编** ——
它和"从系统调用返回"用的是完全相同的代码路径。

这种"用一套机制覆盖两种场景"的设计在内核里到处都是。识别出它们，代码量会小一个数量级。

## 3.4 `sscratch`：无中生有的一个寄存器

trap 一进来，内核面临一个鸡生蛋问题：

- 必须把 `sp` 从用户栈换成内核栈（否则内核就在用户栈上跑了，用户程序可以随便改）
- 但换之前得先把用户栈的值存下来
- 而此刻**没有任何一个寄存器是空闲的** —— 动谁都会毁掉用户程序的现场

RISC-V 给了一个专门的解法：`sscratch` 寄存器。约定是：

```text
  U 态运行期间： sp = 用户栈,  sscratch = 内核栈
  S 态运行期间： sp = 内核栈,  sscratch = 用户栈
```

于是一条原子交换指令就解决了：

```asm
csrrw sp, sscratch, sp
```

一条指令，零额外寄存器，同时完成"切到内核栈"和"保存用户栈"。
`__alltraps` 的第一条和 `__restore` 的最后一条，都是它。

## 3.5 `TrapContext` 与 `#[repr(C)]`

这个结构体由**汇编**填写，由 **Rust** 读取：

```rust
#[repr(C)]
pub struct TrapContext {
    pub x: [usize; 32],   // 偏移 0 .. 255
    pub sstatus: usize,   // 偏移 256
    pub sepc: usize,      // 偏移 264
}
```

汇编里写的是 `sd x1, 1*8(sp)` 这种**硬编码偏移**。而 Rust 默认的 `repr(Rust)`
允许编译器任意重排字段 —— 一旦重排，汇编读到的就是错误的位置，
而且**不会有任何编译错误或运行时报错**，只会得到一堆无法解释的行为。

`#[repr(C)]` 不是可选的优化，是正确性的前提。

顺带解释一个看着浪费的设计：`x[0]` 存了 `x0`，而 `x0` 在 RISC-V 里硬连线为 0，
存它毫无意义。保留这个位置是为了让"**寄存器编号 × 8 = 偏移**"这条规则成立，
汇编里就能写成：

```asm
.macro SAVE_GP n
    sd x\n, \n*8(sp)
.endm
```

8 个字节换来一个能用宏批量展开的规律。

## 3.6 `sepc += 4`

```rust
Trap::Exception(Exception::UserEnvCall) => {
    cx.sepc += 4;
    ...
}
```

`sepc` 指向的是**触发 trap 的那条指令本身**，也就是 `ecall`。
如果原样返回，CPU 会再执行一遍 `ecall`，再次陷入内核 —— 死循环。

所以要手动跳过它。RISC-V 的 `ecall` 固定 4 字节，所以是 `+= 4`。

> 注意这个 `+= 4` 只对 `ecall` 成立。缺页异常就不能跳过 ——
> 内核处理完缺页后要**重新执行**那条访存指令。什么时候跳、什么时候不跳，
> 取决于异常的语义。

## 3.7 内核不能相信用户给的任何东西

`sys_write(fd, buf, len)` 里的 `buf` 是用户程序传进来的地址。
如果内核照单全收地读，用户程序传一个内核地址过来，就能让内核把自己的内存打印出来。

这是一个真实的信息泄露漏洞，[`02bad_syscall_arg`](../user/src/bin/02bad_syscall_arg.rs)
就是干这个的：

```
我要试着让内核把它自己的内存打印给我看。
[ERROR] sys_write：用户程序传来了越界的缓冲区 ptr=0x80200000 len=64，拒绝
sys_write(fd=1, buf=0x80200000, len=64) 返回 -1
被内核拒绝了 —— 这是正确的行为。
```

### 一个我自己踩进去的坑

范围检查的天真写法是：

```rust
start >= APP_BASE && start + len <= APP_BASE + APP_SIZE
```

但用户可以传 `start = 0xffff_ffff_ffff_fff7, len = 64`，让 `start + len` **溢出**绕回
一个很小的数，把检查骗过去。所以必须：

```rust
let Some(end) = start.checked_add(len) else { return false };
```

**而我第一版把同样的错误犯在了错误日志里**：

```rust
error!("越界的缓冲区 [{:#x}, {:#x})", buf as usize, buf as usize + len);
//                                                  ^^^^^^^^^^^^^^^^^^ 又溢出了
```

release 构建下整数溢出会静默绕回，所以第一次运行时日志打出了
`[0xfffffffffffffff7, 0x37)` —— 那个 `0x37` 就是绕回的证据。而 **debug 构建下
整数溢出会 panic**，内核会被自己的一条错误日志搞崩。

教训：**错误处理路径本身也在信任边界上。** 拦住了攻击，却死在了记录攻击的那行代码上。

修法是打印 `ptr` 和 `len` 而不是算出来的区间。现在 `MODE=debug make run` 也能跑完全程。

## 3.8 `run_next_app` 里的作用域陷阱

```rust
pub fn run_next_app() -> ! {
    let app_id = {
        let mut manager = APP_MANAGER.exclusive_access();
        ...
    };  // ← 这个大括号是必须的

    ...
    unsafe { __restore(cx_addr); }   // 一去不回
}
```

`__restore` 直接 `sret` 到用户态，这个函数的栈帧**再也不会被执行**。
如果 `RefMut` 还活着，它的 `Drop` 永远不会运行，`RefCell` 的借用标记
会一直停在"已借出"。等下一个程序 `exit` 时，`exclusive_access()` 直接 panic。

这正是第 2 章选 `RefCell` 而不是裸 `UnsafeCell` 的价值：
它把这个错误变成一个明确的崩溃，而不是悄无声息的数据竞争。

同理，`shutdown(false)` 之前也要 `drop(manager)`。

## 3.9 `fence.i`：把数据当代码写进内存之后

```rust
dst.copy_from_slice(src);
asm!("fence.i");
```

`load_app` 干的事是：把一段字节从内核的 `.data` 段拷到 `0x80400000`，
然后跳过去执行。**我们刚刚把数据当成代码写进了内存。**

CPU 的取指单元有独立的缓存，它可能还存着这块地址的旧内容 —— 也就是上一个程序的指令。
`fence.i` 让 CPU 丢弃指令缓存重新取指。

这个 bug 的麻烦之处在于：**QEMU 的 TCG 未必模拟这个细节，所以在模拟器上能跑**，
一上真机就崩，而且症状是"程序莫名其妙执行了上一个程序的代码"。
属于典型的"能跑但是错的"。

## 3.10 用 GDB 验证

第 3 周计划里写着"第一件事是把 GDB 调起来"。它确实值得：

```bash
# 终端 1
make debug

# 终端 2
make gdb
```

在 `trap_handler` 下个断点，看第一次系统调用发生时的现场：

```
Breakpoint 1, os::trap::trap_handler (cx=0x80222ef0 <os::batch::KERNEL_STACK+7920>)
sepc           0x80400146
scause         0x8

#0  os::csr::scause::read () at src/csr.rs:32
#1  os::trap::trap_handler (cx=0x80222ef0 <os::batch::KERNEL_STACK+7920>) at src/trap/mod.rs:50
#2  0x000000008020006c in __alltraps ()
Backtrace stopped: frame did not save the PC
```

这几行每一项都能对上：

- `scause = 8` —— Environment call from U-mode，用户程序的系统调用
- `sepc = 0x80400146` —— 落在用户程序区（`0x80400000` 起），正是那条 `ecall`
- `cx = KERNEL_STACK + 7920` —— 内核栈 8192 字节，减去 `TrapContext` 的 272 字节，
  正好 7920。**这就是我们在 `__alltraps` 里 `addi sp, sp, -34*8` 腾出来的那块空间**
- `Backtrace stopped: frame did not save the PC` —— 回溯到 `__alltraps` 就断了。
  这不是错误：用户程序的调用栈在**用户栈**上，和内核栈是两个世界。
  `__alltraps` 就是这两个世界的边界

## 3.11 五个用户程序

| 程序 | 干什么 | 预期 |
|---|---|---|
| `00hello_world` | 打印几行，`exit(0)` | 正常退出 |
| `01power` | 10 万次乘法，中途 6 次系统调用 | 算对，现场不乱 |
| `02bad_syscall_arg` | 给 `sys_write` 传内核地址 / 溢出参数 | 被内核拒绝，返回 -1，程序存活 |
| `03bad_instruction` | 在 U 态执行 `sret` 试图提权 | 非法指令异常，被杀 |
| `04bad_address` | 往 `0x0` 写字节 | StoreFault，被杀 |

后两个的关键不在"被杀"，而在**内核没有崩溃**，还能继续跑下一个程序。
这就是操作系统该有的样子。

> 运行 `03bad_instruction` 时 QEMU 会在 stderr 打一行
> `system_opcode_insn: Invalid opcode for CSR read/write instruction`。
> 那是 QEMU 自己的提示，不是我们的输出，可以忽略。

## 3.12 一个必须说清楚的局限

`04bad_address` 能被拦住，靠的是"地址 0 在 QEMU virt 的物理内存图上不存在"，
**而不是因为内核保护了自己**。

本章没有分页，用户程序拿到的就是真实物理地址。如果它往 `0x80200000`
（内核代码段）写，硬件不会有任何意见，内核会被悄无声息地改写。
`is_user_accessible` 只能拦住**通过系统调用**进来的越界访问，
拦不住用户程序直接解引用。

所以这一章的"隔离"是**纸糊的**。真正的隔离要等第 7–8 周建立地址空间 ——
只有让用户程序看到的地址和物理地址分开，硬件才能强制执行边界。

诚实地承认这一点比假装已经安全重要。

## 3.13 内存布局的变化

```diff
- .data            [0x008020a000, 0x008020a000)        0 B
+ .data            [0x008020a000, 0x0080210000)    24576 B  (  24 KiB)
```

`.data` 从 0 涨到 24 KiB —— 那是五个用户程序的二进制，由 `build.rs` 生成的
`link_app.S` 用 `.incbin` 直接嵌进了内核镜像。

本章还没有文件系统，内核没有任何办法"读取"一个程序文件，
只能在编译期把它们塞进自己的 `.data` 段里带着走。
第 13 周做完文件系统后，用户程序才能改从磁盘加载。

## 3.14 练习

1. **删掉 `cx.sepc += 4`**，看会发生什么。你会看到第一句 `println!` 被无限重复 ——
   因为程序永远卡在同一条 `ecall` 上。
2. **在 `app_init_context` 里不清 `SPP`**，程序会以 S 态运行。
   这时 `03bad_instruction` 的 `sret` 就不再是非法指令了 —— 试试看它会跳到哪。
3. **故意写错 `__alltraps`**：把 `SAVE_GP` 的循环从 `.rept 27` 改成 `.rept 26`，
   于是 `x31` 不被保存。用 GDB 找出它是怎么崩的 —— 这就是本章最真实的调试体验。
4. **把 `04bad_address` 的目标地址改成 `0x80200000`**（内核代码段），
   观察内核被改写后会发生什么。这是 3.12 节那个局限的实地演示。
5. **加一个 `sys_get_time` 系统调用**（调用号 169），让用户程序能读到时间。
   这会是第 5 周时间片轮转的基础。

第 4 章：**多道程序**。

现在的批处理系统，一个程序不跑完，下一个就没机会。第 4 章要让多个程序
同时待在内存里，通过 `sys_yield` 主动让出 CPU，轮流执行。
