# 第 5 章　抢占式调度：给 CPU 装闹钟

> 对应 tag `v0.5`。本章代码：`git diff v0.4..v0.5`

## 5.1 这一章要解决的问题

第 4 章的协作式调度有个致命弱点：**调度器完全依赖任务自觉**。
一个不调 `yield` 的任务能一直占着 CPU，一个 `loop {}` 能把整个系统卡死。

这一章给 CPU 装个闹钟。每隔一个时间片，硬件强行把控制权交还内核，
内核就能把 CPU 从任何任务手里夺回来 —— 不管它愿不愿意。

**用户程序一个字都不用改。** 改的是内核。这正是"抢占"的含义。

## 5.2 时间从哪来

RISC-V 提供一个只读的 `time` CSR，每个时钟周期加一。QEMU virt 上它的频率是
10 MHz —— 这个数字不是猜的，是开机时 OpenSBI 自己打印的：

```
Platform Timer Device : aclint-mtimer @ 10000000Hz
```

而"什么时候响"由 `mtimecmp` 寄存器决定：`time >= mtimecmp` 时触发时钟中断。

但 `mtimecmp` 是 **M 态资源**，S 态的内核碰不到。所以又得请固件代劳 ——
SBI 的 `set_timer`。这和第 1 章打印字符是同一个模式：**内核想干的事超出了
自己的权限，就向下一层求助**。

```rust
pub fn set_next_trigger() {
    set_timer(get_time() + CLOCK_FREQ / TICKS_PER_SEC);
}
```

`TICKS_PER_SEC = 100`，时间片 10 ms，和 Linux 默认的 `HZ=100` 一致。

## 5.3 一个容易搞错的特权级规则

要抢占用户程序，直觉上似乎该把中断全打开：`sie.STIE` 和 `sstatus.SIE` 都置位。

**但只需要 `sie.STIE`。**

RISC-V 特权级规范里有这么一条：

> 当 hart 运行在特权级 x 时，**更高**特权级 y > x 的中断**永远是全局开启的**，
> 与该级的全局使能位无关。

也就是说，CPU 在 U 态执行时，S 态中断本来就开着，`sstatus.SIE` 根本不参与判断。
所以打开 `sie.STIE` 之后，用户程序就已经能被时钟中断抢占了。

而 `sstatus.SIE` 管的是**"CPU 正在 S 态执行时是否响应中断"** —— 也就是内核自身
是否可被抢占。我们刻意保持它为 0。

## 5.4 顺便把第 2 章欠的账结了

第 2 章给 `UPSafeCell` 写了一条注释：

> 前提在第 5 周开启时钟中断后会变弱（中断处理程序可能重入），
> 到时候需要升级成"访问期间关中断"。现在先记下这笔账。

这笔账现在怎么还？答案有点出人意料：**我们通过"决定内核不可抢占"来偿还它，
而不是给每个临界区加关中断。**

因为 `sstatus.SIE = 0`，内核执行期间到达的时钟中断会被**挂起（pending）**，
等 `sret` 回到用户态的那一刻才被送达 —— 一个都不会丢，但也一个都不会在
内核临界区中间插进来。于是：

- 内核里的临界区天然是原子的
- `UPSafeCell` 的"不被抢占"前提得以保住，一行代码都不用改

代价是：内核里一段长耗时的操作会推迟**所有**任务的调度。
Linux 在 2.6 之前也是这么做的，后来才引入可抢占内核。

这是一个明确的设计决定，不是偷懒。写下来，比假装问题不存在重要。
真正需要还这笔账的时候是引入多核 —— 那时单核假设彻底崩塌，
必须换成真正的自旋锁。

## 5.5 中断不是异常：不要动 `sepc`

第 3 章处理 `ecall` 时有一句 `cx.sepc += 4`，跳过那条已经执行完的 `ecall`。

时钟中断**绝不能这么做**：

```rust
Trap::Interrupt(Interrupt::SupervisorTimer) => {
    set_next_trigger();
    // 注意这里不动 sepc
    suspend_current_and_run_next();
}
```

因为被打断的那条指令**还没执行完**。任务恢复时必须重新执行它。
加了 `+= 4` 的话，用户程序每被抢占一次就会跳过一条指令 —— 而且是随机的某条，
症状诡异到无法调试。

一般规律是：**看这个 trap 的语义是"已经做完了"还是"没做成"**。
`ecall` 属于前者（服务已提供），缺页和中断属于后者（要重来）。

## 5.6 闹钟是一次性的

```rust
set_next_trigger();          // ← 必须在切走之前
suspend_current_and_run_next();
```

SBI 的定时器响过就没了。每次处理完时钟中断，必须立刻再设下一次。

忘了重设的症状很有迷惑性：**第一次抢占成功，之后再也不抢占了**。
系统看起来是工作的，只是行为退化回了协作式调度。

顺序也有讲究：必须在 `suspend_current_and_run_next()` **之前**设闹钟，
因为那个调用会把执行流切走，后面的代码要等很久才轮得到执行。

## 5.7 三条路径，一个出口

现在任务让出 CPU 有三条路径：

```text
  sys_yield  ─┐
  sys_exit   ─┼─→  schedule_next()  ─→  __switch
  时钟中断    ─┘
```

它们最终都汇到同一个 `schedule_next`。无论是"我主动让"还是"被硬件夺走"，
切换动作本身完全一样 —— 差别只在于是谁触发的。

这又是一次"用一套机制覆盖多种场景"。第 3 章是"启动程序 = 从 trap 返回"，
第 4 章是"`ra` 的两种语义"，这一章是"三种让出，一个调度器"。

## 5.8 量化证据

光看到输出交错还不够 —— 那可能只是巧合。所以 `04spin_x` 和 `05spin_y`
每段计算都打印**墙钟耗时**。每段的工作量是固定的，独占 CPU 时耗时也该固定，
那么多出来的部分就是被别人占走的：

```
  [X] 第 0 段算完，墙钟 42 ms      ← A/B/C、计时程序都在跑
  [Y] 第 0 段算完，墙钟 36 ms
  ...
  [X] 第 2 段算完，墙钟 27 ms      ← A/B/C 退出了，只剩 X 和 Y
  [Y] 第 3 段算完，墙钟 25 ms
  [X] 第 3 段算完，墙钟 27 ms
  [Y] 第 4 段算完，墙钟 25 ms
  ...
  [Y] 全部算完，总墙钟 166 ms
  [X] 第 5 段算完，墙钟 21 ms      ← Y 退出了，X 独占
  [X] 全部算完，总墙钟 183 ms
```

读这组数字：

- 一段计算独占 CPU 约需 **12.5 ms**
- 只有 X 和 Y 时，每段墙钟稳定在 **25–27 ms** —— **正好 2 倍**。
  两个任务平分 CPU，这是时间片轮转最直接的数值证明
- 任务多的时候（A/B/C 也在跑）涨到 36–42 ms
- Y 退出后 X 的最后一段掉到 **21 ms** —— 独占了

**这两个程序一次都没调 `yield`。** 在第 4 章，X 会一口气跑完 6 段，
Y 才有机会开始。

## 5.9 `loop {}` 不再能卡死系统

第 4 章练习里有一条"把霸占者的主体换成 `loop {}`，观察整个系统卡死"。
这一章把同样的程序放进来实测：

```
  [死循环] 我进入 loop {}，永不退出，也永不 yield。
  ...
  [A] 四轮跑完，退出
  [B] 四轮跑完，退出
  [C] 四轮跑完，退出
  [Y] 全部算完，总墙钟 418 ms
  [X] 全部算完，总墙钟 457 ms
```

死循环任务启动之后，**其余任务全部正常跑完**。系统不会关机 ——
因为那个任务永远处于 `Ready`，调度器永远有活干 —— 但它再也不能
阻止别人推进了。

另一个细节：X 的总墙钟从 183 ms 涨到 457 ms。多了一个一直抢 CPU 的任务，
每个人分到的份额自然变少。数字是自洽的。

## 5.10 时间片长度的权衡

`TICKS_PER_SEC = 100`（10 ms）不是随便定的：

| 时间片 | 好处 | 代价 |
|---|---|---|
| 短（1 ms） | 响应及时，交互流畅 | 每次切换都要保存/恢复现场、走调度器，开销占比高 |
| 长（100 ms） | 切换开销摊薄，吞吐高 | 一个任务能霸占很久，交互明显卡顿 |

10 ms 是个经过几十年验证的折中，Linux 的默认 `HZ` 也是 100。

另外，`06timer` 的输出暴露了一个有意思的现象：

```
  [计时] 忙等 50 ms 期间，我主动让出了 3 次 CPU。
```

50 ms 里只 yield 了 3 次？因为每次 `yield` 之后，X 和 Y 各要跑满一个时间片
才轮得回来 —— 一轮往返就是十几毫秒。**在多任务系统里，"让出 CPU" 的代价
远高于一次函数调用**，这也是为什么真正的 `sleep` 需要等待队列，
而不是忙等着 yield。

## 5.11 练习

1. **把 `TICKS_PER_SEC` 改成 1000**（时间片 1 ms），对比 X/Y 的墙钟数字。
   切换更频繁了，但总耗时会变长 —— 多出来的就是切换开销。
2. **改成 10**（时间片 100 ms），看输出交错变得多粗。
3. **故意在时钟中断分支里加上 `cx.sepc += 4`**，观察用户程序如何崩溃。
   用 GDB 看 `sepc` 是怎么跑偏的。
4. **注释掉 `set_next_trigger()`**，验证"第一次抢占成功，之后退化成协作式"
   这个症状。这是本章最容易犯又最难发现的错误。
5. **试着打开 `sstatus.SIE`**（让内核也可被抢占），然后在
   `schedule_next` 的临界区里加一个长循环。你应该能看到 `UPSafeCell`
   的 `already borrowed` panic —— 那正是第 2 章记下的那笔账。
6. **统计抢占次数**：在时钟中断分支里加计数器，和 `sys_yield` 的次数分开统计，
   退出时打印。看看两种让出方式的比例。

## 5.12 阶段小结

到这里，**阶段 I（裸机与陷入）全部完成**：

| 周 | 成果 |
|---|---|
| 1 | 从上电到 Rust，SBI 输出 |
| 2 | 内核堆，`alloc` 容器可用 |

现在 CCNUOS 已经是一个能同时运行多个不受信任程序、并公平分配 CPU 的系统了。

但它还有一个根本缺陷：**没有内存隔离**。用户程序拿到的是真实物理地址，
往内核段写不会被任何东西阻止；程序之间也只隔着一个软件检查。

阶段 II（第 6–9 周）就是要解决这件事。第 6 章先做地基：
物理页帧分配器和 SV39 多级页表。
