# 第 7 章　开启分页

> 对应 tag `v0.7`。本章代码：`git diff v0.6..v0.7`

## 7.1 本章的策略：先让语义完全不变

开启分页是那种一步到位就很容易翻车的改动 —— 一旦 `satp` 写下去，
每一次取指、每一次访存都变了含义，出了问题几乎无从下手。

所以这一章刻意保守：**建立一个把所有物理内存恒等映射（虚拟地址 = 物理地址）
的内核地址空间，然后打开分页。** 系统的行为应该和第 6 章一模一样，
只是所有访存都多走了一趟 MMU。

这样做有两个好处：

1. 出了问题，一定是在"开启分页"这件事本身上，而不是混在别的改动里
2. 即便如此保守，我们**已经拿到了真正的硬件保护** —— 见 7.6 节

第 8 章才会给每个进程建独立的地址空间，那时才需要跳板页。

## 7.2 `activate()`：内核里最危险的一个函数

```rust
pub unsafe fn activate(&self) {
    satp::write(self.token());
    asm!("sfence.vma", options(nostack));
}
```

两行代码，但第一行执行完之后，**取下一条指令就要走新页表了**。

这意味着：如果新页表里没有"当前正在执行的这段代码"，CPU 会立刻取指失败 ——
而且此时连 trap 处理程序都可能取不到，直接原地打转，连报错的机会都没有。

恒等映射让这件事变得平凡：`.text` 映射到它自己的物理地址，
所以 `pc` 在切换前后指向同一个地方。`sp` 同理（启动栈在 `.bss` 里，
也是恒等映射的）。

有一处细节容易漏：映射 `.bss` 要用 `sbss_with_stack` 而不是 `sbss`。
启动栈就在两者之间，不映射它的话，开启分页后第一次压栈就会缺页。

第二行 `sfence.vma` 也不能省。TLB 里缓存着旧页表的翻译结果，不刷的话
CPU 可能继续用旧映射，行为完全不可预测。

## 7.3 内核空间的八个段

```
  内核空间 .text        [0x80200000, 0x8020d000)  R-X
  内核空间 .rodata      [0x8020d000, 0x80211000)  R--
  内核空间 .data        [0x80211000, 0x8022d000)  RW-
  内核空间 .bss+stack   [0x8022d000, 0x8055f000)  RW-
  内核空间 空洞          [0x8055f000, 0x80800000)  RW-
  内核空间 用户程序区     [0x80800000, 0x80a00000)  RWXU
  内核空间 用户栈区       [0x80a00000, 0x80a20000)  RW-U
  内核空间 空闲页帧       [0x80a20000, 0x88000000)  RW-
```

每一段的权限都是按实际用途给的最小集合：

- **`.text` 是 `R X` 而不是 `R W X`** —— 内核代码不可写。这一条挡住了
  一整类攻击（改写内核代码）
- **`.data` / `.bss` 是 `R W` 而不是 `R W X`** —— 数据段不可执行。
  挡住了另一类攻击（把数据当代码跳进去）
- **只有用户程序区和用户栈区带 `U`** —— 这一位就是内存隔离的硬件开关

第 6 章之前，整个物理内存对所有人都是无限制的。现在有了分层。

## 7.4 用户栈必须搬出内核 `.bss`

这是开启分页逼出来的一个改动。

"用户能不能访问某一页"由页表项的 `U` 位决定。而内核 `.bss` 整体是不带 `U` 的
（里面有内核堆、内核栈这些绝不能给用户碰的东西），如果用户栈混在里面，
就没法只给它单独开 `U`。

所以用户栈搬进了一块自己的物理区域（`0x80a00000` 起）。内核栈仍然留在
`.bss` —— 它本来就只有内核能碰。

副产品是内存布局变得一目了然：**哪些内存是给用户的，从地址上就能看出来。**

## 7.5 从 ELF 装载，而不是拷贝裸字节

之前几章装载用户程序的办法是"把一段裸字节拷到固定地址"。那样有两个问题：

1. 不知道程序的入口在哪，只能假定它等于加载地址
2. 不知道哪一段是代码、哪一段是数据 —— 只能给整块内存同时开读写执行

ELF 把这些信息都写在**程序头表**里。解析之后：

```
  [0] 2 个段，入口 0x0080800000，槽位 0x0080800000
      段 R-X  [0x0080800000, 0x0080800c78)  文件 3192 字节，内存 3192 字节
      段 R--  [0x0080801000, 0x00808012dd)  文件  733 字节，内存  733 字节
```

代码段是 `R-X`，只读数据段是 `R--`。第 8 章给每个进程建独立地址空间时，
这些权限会被原样搬进页表 —— 那时用户程序才真正拿到分段保护。

`memsz > filesz` 的差额就是 `.bss`：它在文件里不占空间（存一堆 0 没意义），
但装载时必须补零。我们的装载器是先把整个槽位清零再拷贝，正好一并解决。

### 解析不可信输入

用户程序的 ELF 是不可信输入。一个构造出来的文件完全可以把段的目标地址
指到内核里。所以拷贝**之前**必须验：

```rust
let seg_end = ph.vaddr.checked_add(ph.memsz).expect("段的目标地址溢出");
assert!(ph.vaddr >= base && seg_end <= limit, "...越出了它的槽位...");
```

`ElfFile::parse` 里也有一串校验：魔数、64 位、小端、RISC-V 目标、
程序头表必须完整落在文件内。这些不是形式主义 —— 内核即将把这段字节
当作**代码**执行。

## 7.6 这一章白拿的一份保护

虽然内核和用户还共用一个地址空间，但只要用户程序区带 `U` 而内核不带，
硬件就已经能挡住用户程序直接访问内核内存了。

`10bad_kernel_write` 就是来验证这件事的。同一份代码：

| 章节 | 结局 |
|---|---|
| 第 3–6 周 | **写成功**，内核被悄无声息地改写，而且察觉不到 |
| 第 7 周起 | `StorePageFault`，进程被杀，内核毫发无损 |

```
  [越权] 我要直接往内核代码段 0x80200000 写一个字节。
  [越权] 第 6 周之前这会成功，而且内核不会察觉。
[ERROR] 用户程序访存出错：StorePageFault，地址 0x80200000 —— 杀掉，换下一个
```

注意它和 `07bad_syscall_arg` 的区别，两者堵的是**不同的洞**：

| | 谁在访存 | 靠什么拦 |
|---|---|---|
| 直接解引用内核地址 | 用户态 | **MMU 的 `U` 位** |
| 把内核地址当系统调用参数传进来 | 内核态 | **软件范围检查** |

第二条路绕过了 MMU —— 因为访存是内核自己做的，而内核当然有权限。
所以 `is_accessible_by` 那个软件检查一天都不能省。

## 7.7 踩的坑之一：S 态默认不能访问 U 页

第一次开启分页，内核在装载用户程序时立刻崩了。

原因是 `sstatus.SUM`（permit Supervisor User Memory access）默认为 **0**：
**S 态不能访问带 `U` 位的页。**

这其实是一条很好的保护 —— 内核不小心解引用了一个用户指针时，硬件会立刻
拦下来，而不是让它悄悄读写用户内存。

但本章的设计（内核和用户共用一个地址空间）绕不过它：内核要往带 `U` 的页里
装载程序、要读用户传来的系统调用缓冲区。所以只能打开 `SUM`。

**这是本章设计的一个真实代价，而不是一个无所谓的开关。** 第 8 章给每个进程
建独立地址空间后，内核改用手动查页表的方式访问用户内存，这一位就能关掉。

## 7.8 踩的坑之二：`__alltraps` 毁掉了犯罪现场

上面那个 `SUM` 的问题，报出来的现场是这样的：

```
[ERROR] 用户程序访存出错：StorePageFault，地址 0xfffffffffffffef8，指令位于 0x8020503e
```

三处都不对：不是用户程序、地址不知所云、指令位置也不是真正出错的地方。

推一下就清楚了。`stvec = 0x80205038`，而报出的 `pc = 0x8020503e` 正好在
`__alltraps` 开头 6 字节处。而 `__alltraps` 的第一条指令是：

```asm
csrrw sp, sscratch, sp
```

它**假定 trap 一定来自用户态**，上来就把 `sp` 和 `sscratch` 对调。
启动阶段 `sscratch` 还是 0，于是 `sp` 变成 0，再 `addi sp, sp, -34*8`
得到 `-272`，第一条 `sd x1, 1*8(sp)` 就写到了 `0xfffffffffffffef8`。

**真正的故障被 trap 处理程序自己的第一条指令彻底掩盖了。**

### 修法：内核态另设一个 trap 入口

```asm
    .align 2
    .globl __kernel_trap
__kernel_trap:
    call    kernel_trap_handler
```

什么都不换，带着当前完好的内核栈直接去 panic。这样 `scause` / `stval` / `sepc`
都还是第一现场。

切换时机：

- `trap::init()` 把 `stvec` 指向 `__kernel_trap`
- `trap_handler` 开头也切回内核态入口（万一处理 trap 时内核自己又出错）
- **`__restore` 开头**切回 `__alltraps`

最后一条是关键。放在 `__restore` 而不是 `trap_handler` 末尾，是因为
**所有**进入用户态的路径都会经过 `__restore` —— 既包括处理完 trap 返回，
也包括任务第一次被调度（`__switch` 的 `ret` 直接跳进来）。
少覆盖一条路径，就会出现"某个任务的第一次系统调用把内核打飞"这种
极难复现的 bug。

### 效果对比

故意让内核写一个没映射的地址，两种报法：

```
修之前：  用户程序访存出错：StorePageFault，地址 0xfffffffffffffef8，指令位于 0x8020503e
修之后：  内核自身触发了 trap：Exception(StorePageFault)
          scause=0xf  stval=0x40000000  sepc=0x80206852
```

`stval=0x40000000` 正是我写的那个地址，`sepc` 也指向真正出错的指令。

> 这个改动的价值不在本章 —— 在第 8 章。那一周要重写整个 trap 路径，
> 内核态的故障会成为家常便饭。**在开始一段困难的工作之前，
> 先把它的调试手段准备好。**

## 7.9 页表的账单

```
分页已开启：satp = 0x8000000000080a03，8 个逻辑段，页表自身占 65 页（已开 SUM）
```

65 页 = 260 KiB，用来映射 128 MiB 物理内存。比例大约 1:500。

这个数字完全由第 6 章那条规律决定：恒等映射的地址是连续的，
所以中间级页表被最大限度地复用了。如果换成随机地址，同样的页数会爆炸。

## 7.10 练习

1. **把 `.text` 的权限改成 `R | W | X`**，然后在内核里写一句
   `unsafe { (0x80200000 as *mut u8).write_volatile(0) }`。
   对比改回 `R | X` 之后的行为。
2. **注释掉 `add(".bss+stack", ...)` 里的 `sbss_with_stack`，改用 `sbss`**，
   看开启分页后内核在哪一步崩。用新的 `__kernel_trap` 现场分析。
3. **去掉 `activate()` 里的 `sfence.vma`**，观察是否还能正常工作。
   （QEMU 可能不严格模拟 TLB，所以不一定复现 —— 这恰恰说明为什么
   "在模拟器上能跑"不等于正确）
4. **关掉 `SUM`**，看内核在装载程序的哪一步崩。这是 7.7 节那个坑的复现。
5. **给 `ElfFile::parse` 喂一个构造的恶意 ELF**（比如把某个段的 `p_vaddr`
   改成 `0x80200000`），验证装载器会拒绝它。

## 7.11 下一章

第 8 章：**跳板页**，全项目最难的一周。

要做的事：给每个进程建独立的地址空间，内核和用户不再共享页表。

难点在于 trap 发生时需要换页表（用户空间 → 内核空间），而**切换 `satp` 的
那条指令执行完之后，取下一条指令用的已经是新页表了**。所以这段代码必须
在两个地址空间里位于**同一个虚拟地址** —— 这就是"跳板页"。

做完之后，`SUM` 就能关掉了。
