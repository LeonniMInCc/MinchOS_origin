# 第 9 章　进程管理：fork / exec / waitpid

> 对应 tag `v0.9`。本章代码：`git diff v0.8..v0.9`
>
> 阶段 II 的最后一周。做完之后，CCNUOS 有了完整的进程模型。

## 9.1 从"任务表"到"进程树"

第 4–8 周的"任务"是编译期就定好的一张表：内核开机时把所有程序一股脑做成
任务扔进调度器，数量固定，编号就是下标。

这一章改成真正的进程模型：内核**只创建一个进程**（`initproc`），
其余全部由它 `fork` 出来。

```text
  initproc (pid 0)
    ├── pid 1  00hello_world
    ├── pid 2  01yield_a
    ├── ...
    └── pid 12 11forktest
                 └── pid 10   ← fork 出来的孙进程
```

这带来一连串连锁改动，每一处都值得想清楚。

## 9.2 PID 要动态分配了

编号不再是下标，因为进程运行时才被创建、退出时又会让出编号。所以需要一个
分配器，而且和第 6 章的页帧分配器用了**完全相同的套路**：

```rust
pub struct PidHandle(pub usize);

impl Drop for PidHandle {
    fn drop(&mut self) { PID_ALLOCATOR.exclusive_access().dealloc(self.0); }
}
```

持有它就等于占着这个号，它被丢弃时号自动归还。

这一点在进程模型里比在页帧里更重要：进程退出的路径有好几条（正常 `exit`、
被非法指令杀掉、被访存错误杀掉），每条都记得释放 PID 是不现实的。

内核栈同理 —— `KernelStack` 的 `Drop` 会把它在内核地址空间里的映射解除、
归还物理页帧。

运行日志里能直接看到复用：

```
[fork] 父进程 pid=12，fork 返回 10（子进程的 PID）
```

pid 10 原本属于 `09bad_address`，它退出并被回收后号就还回了分配器。

## 9.3 PCB 要能互相引用

父进程持有子进程，子进程指回父进程。这必然要用 `Arc`，而 `Arc` 里的东西
不可变 —— 所以把需要改的字段收进一个 `UPSafeCell`：

```rust
pub struct TaskControlBlock {
    pub pid: PidHandle,              // 创建后不变
    pub kernel_stack: KernelStack,   // 创建后不变
    inner: UPSafeCell<TaskControlBlockInner>,
}
```

有一个地方**必须**用 `Weak` 而不是 `Arc`：

```rust
pub parent: Option<Weak<TaskControlBlock>>,
pub children: Vec<Arc<TaskControlBlock>>,
```

父子互相强引用的话，引用计数永远降不到 0，两个进程的内存谁都释放不掉。
**父子关系里"拥有"的方向是单向的：父进程拥有子进程。**

## 9.4 调度模型改成了"任务 ↔ idle"

第 4–8 周是**任务直接切到任务**：A 让出 CPU 时自己挑好下一个 B，
然后 `__switch(A, B)`。

第 9 周改成经过一个 idle 控制流中转：

```text
  任务 A ──__switch──▶ idle ──__switch──▶ 任务 B
```

多了一次切换，为什么反而更好？

- **让出的一方不必知道下一个是谁。** 进程退出时尤其明显：它已经是僵尸了，
  让它自己去挑下一个任务很别扭
- **"就绪队列为空"有了自然的处理位置。** idle 发现队列空了就停在那里，
  不需要在每个让出点都判断一次
- **idle 跑在启动栈上**，不属于任何进程 —— 所以进程的内核栈可以被安全回收

这是操作系统里反复出现的模式：**多引入一层间接，换来职责的分离。**

## 9.5 `fork`：一次调用，两次返回

```rust
pub fn fork(self: &Arc<Self>) -> Arc<Self> {
    let memory_set = MemorySet::from_existed_user(&parent_inner.memory_set);
    // ... 新 PID、新内核栈 ...
}
```

`from_existed_user` 逐段复制：形状（虚拟地址范围、权限）照搬，
物理页帧全部重新分配，内容一页一页拷过去。

结果是两个**布局完全相同、内容完全相同、但互不影响**的地址空间。
父子之间唯一的差别有三处：

1. 新的 PID 和新的内核栈
2. `TrapContext.kernel_sp` 指向子进程自己的内核栈
3. 系统调用返回值：父进程拿到子进程 PID，子进程拿到 0

第 3 条就是那个著名的"一次调用、两次返回"。实现上一点也不神秘 ——
`fork_current` 直接把 0 写进子进程 `TrapContext` 的 `a0`：

```rust
child.inner_exclusive_access().trap_cx().x[10] = 0;
```

子进程压根没有"执行完一次系统调用"，只是被布置成了仿佛刚执行完的样子。
和第 3 章"启动程序 = 从一次不存在的 trap 返回"是同一个思路。

第 2 条容易漏。`TrapContext` 是连同地址空间一起拷过来的，里面的 `kernel_sp`
还是父进程的内核栈 —— 不改的话，子进程第一次陷入内核就会跑到父进程的栈上，
两个进程同时用一个内核栈，后果不堪设想。

### 验证

`11forktest` 直接把这三件事演出来：

```
  [fork] 我是 pid 12，MARK @ 0x13000 = 0xf00d
  [fork] 父进程 pid=12，fork 返回 10（子进程的 PID）
  [fork] 子进程 pid=10，fork 返回 0，把 MARK @ 0x13000 改成 0xbeef
  [fork] 父进程的 MARK @ 0x13000 仍是 0xf00d
  [fork] 父进程回收了 pid 10，退出码 42
```

**同一个虚拟地址 `0x13000`，父子各自一份。** 子进程改自己那份，父进程
纹丝不动。

> 顺带一提，这也解释了为什么真实系统的 `fork` 要用写时复制优化：
> 这里每 `fork` 一次就实打实拷贝整个地址空间，而绝大多数子进程紧接着就
> `exec`，把刚拷来的东西整个丢掉。`initproc` 干的正是这件事，
> 12 次里有 12 次是白拷。

## 9.6 `exec`：换装而不换身份

```rust
pub fn exec(&self, elf_data: &[u8]) {
    let (memory_set, user_sp, entry) = MemorySet::from_elf(elf_data);
    let mut inner = self.inner_exclusive_access();
    inner.memory_set = memory_set;   // ← 旧地址空间在这一行被 Drop
    // ...
}
```

PID、父子关系、内核栈全都不变 —— 变的只是"这个进程在执行什么"。
旧的 `MemorySet` 在赋值时被丢弃，它占的物理页帧全部自动归还。

有一处细节在第 8 章就埋好了伏笔。`trap_handler` 里：

```rust
let result = syscall(id, args);
// 重新取一次
current_trap_cx().x[10] = result as usize;
```

当时写"重新取"只是为了代码更清楚。到了这一章它变成了**必需的** ——
`sys_exec` 会把整个地址空间换掉，`trap_cx_ppn` 也跟着变了。
用旧引用去写返回值的话，写的是那个已经被释放的地址空间里的页。

## 9.7 僵尸进程：为什么不能一 `exit` 就消失

退出码是给父进程看的。如果进程一 `exit` 就彻底消失，父进程的 `wait`
就永远拿不到结果了。

所以退出分成两步：

1. **`exit` 时**：状态变 `Zombie`，退出码存进 PCB，
   **用户内存立刻归还**（死掉的进程没理由继续占着几 MiB）
2. **父进程 `waitpid` 时**：把它从 `children` 里移除 →
   引用计数归零 → `PidHandle` 和 `KernelStack` 的 `Drop` 触发

第 2 步全靠 RAII 自动完成。手写这段回收逻辑的话，四五条退出路径里
漏掉任何一条都会造成泄漏。

代码里还加了一条断言，把这个不变量钉死：

```rust
let child = inner.children.remove(idx);
assert_eq!(Arc::strong_count(&child), 1, "回收进程 {} 时还有别人持有它的引用", ...);
```

如果哪天有人不小心在别处存了一份 `Arc`，这条断言会立刻叫出来 ——
而不是等到几小时后发现内存莫名其妙少了。

## 9.8 孤儿进程要有人收养

进程退出时如果还有活着的子进程，那些子进程就成了孤儿。不管的话，
它们退出后会变成**没人 `wait` 的僵尸**，PCB、PID、内核栈永远回收不掉。

Unix 的做法是过继给 `init`。我们照搬：

```rust
if !is_initproc && !inner.children.is_empty() {
    let foster = initproc();
    for child in inner.children.iter() {
        child.inner_exclusive_access().parent = Some(Arc::downgrade(&foster));
        foster_inner.children.push(Arc::clone(child));
    }
}
```

## 9.9 `waitpid` 为什么会返回 -2

内核的 `sys_waitpid` 在"子进程还活着"时返回 **-2** 而不是阻塞等待。
因为还没有等待队列 —— 那是第 14 章的事。

用户库自己循环 `yield` 重试：

```rust
pub fn waitpid(pid: isize, exit_code: &mut i32) -> isize {
    loop {
        match sys_waitpid(pid, exit_code as *mut i32) {
            -2 => yield_now(),
            n => return n,
        }
    }
}
```

语义完全一样，只是浪费些 CPU。**能用简单方案先跑通的，不必一步到位。**
把"忙等"留在用户库里，等第 14 章有了等待队列，改一个函数就能升级成真正的阻塞。

## 9.10 端到端的泄漏检查

这一章新增了这么多要回收的东西（地址空间、页表、PID、内核栈、PCB），
光靠代码审查很难确信没漏。所以加了一个开关机对照：

```rust
mm::record_baseline();   // 用户态启动前
task::add_initproc();
task::run_tasks()        // ... 全部进程跑完 ...
// idle 发现队列空了：
task::release_initproc();
mm::report_leak();
```

结果：

```
[INFO] 就绪队列已空，全部进程执行完毕
[INFO] 页帧核对：67 页，与用户态启动前完全一致，无泄漏
```

**13 个进程 fork、exec、退出、回收之后，每一页物理内存都回来了。**

这个检查第一次跑时是**失败**的 —— 报"多出 7 页"。查下来不是真泄漏：
`initproc` 退出后变成僵尸，但它没有父进程，没人 `waitpid` 它，
引用只剩内核里那个 `INITPROC` 静态变量。于是它的页表和内核栈一直占着。

修法是关机前主动撒手（`release_initproc()`）。这也顺带说明：
**"没人回收的进程"这个问题，对 `initproc` 自己同样成立。**

## 9.11 练习

1. **把 `parent` 从 `Weak` 改成 `Arc`**，跑一遍看泄漏检查报多少页。
   想清楚引用计数是怎么卡住的。
2. **去掉 `fork` 里那句 `trap_cx().kernel_sp = kernel_sp`**，
   观察子进程第一次陷入内核时发生什么。用 GDB 看两个进程的 `sp`。
3. **去掉孤儿过继那段**，然后写一个 fork 出子进程就立刻退出的程序，
   看泄漏检查报什么。
4. **让 `initproc` 不 `wait` 就退出**，观察就绪队列空了但页帧对不上。
5. **给 `sys_waitpid` 加一个 `WNOHANG` 标志**，让它在子进程没退出时
   立刻返回 0 而不是 -2，然后在用户侧实现一个轮询版的 `wait`。
6. **实现写时复制**：`fork` 时不拷贝物理页，只把父子双方的页表项都改成
   只读；写的时候触发缺页异常，在 `trap_handler` 里才真正分配并拷贝。
   这是本项目里最值得做的一道进阶题。

还缺什么？它没有交互 —— 跑什么程序在编译期就写死在 `initproc` 里。
也没有文件：程序只能从内核镜像里取。

阶段 III（第 10–13 周）解决这两件事。第 10 章先做 shell：
有了 `fork` + `exec`，再加上一个 `sys_read`，就能敲命令了。
