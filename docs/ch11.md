## 11.3 管道怎么"连接"两个进程

关键在第 10 章埋下的一件事：**`fork` 复制文件描述符表，但共享底下的
文件对象**。

```text
  shell: pipe() → fd 3 (读端), fd 4 (写端)
    │
    ├─ fork → 子进程 A：close(1), dup(4) ⇒ 它的 stdout 就是管道写端
    └─ fork → 子进程 B：close(0), dup(3) ⇒ 它的 stdin  就是管道读端
```

两个子进程各自的 fd 号完全不同，但 `Arc` 指向**同一个环形缓冲区**。
A 往 stdout 写，B 从 stdin 就读到了。

最妙的是：**A 和 B 都不知道自己在管道里。** `12words` 只管往 fd 1 写，
`14wc` 只管从 fd 0 读，两者都以为自己在跟终端打交道。
"连接"这件事完全发生在 shell 里，发生在 `exec` 之前。

## 11.4 "关掉再复制"这个惯用法

```rust
close(STDOUT);              // 释放 fd 1，它成为最小的空闲号
dup(pipes[i][1] as usize);  // 于是新副本必然落在 1 上
```

这套几十年来的写法，完全建立在一条 POSIX 规定上：
**`dup` 返回当前最小的空闲 fd**。

所以第 10 章 `alloc_fd` 里那句"总是返回最小的可用 fd"不是实现细节，
是一条必须遵守的契约。换成"随便找个空位"的话，整套惯用法就全垮了。

## 11.5 EOF 是怎么判断的

读端读到空缓冲区时，要区分两种情况：

- **写端还在**：数据只是还没来，应该等
- **写端全关了**：再也不会有数据了，返回 0 表示 EOF

所以缓冲区里存了指向两端的 `Weak` 引用：

```rust
fn all_write_ends_closed(&self) -> bool {
    self.write_end.as_ref().map(|w| w.upgrade().is_none()).unwrap_or(true)
}
```

用 `Weak` 而不是 `Arc`：缓冲区被两端持有，要是它反过来强引用两端，
引用计数就永远降不到 0 —— 和第 9 章父子进程那个循环引用是同一个问题。
**这个模式在这个项目里出现第三次了**（父子进程、管道两端、还有
`INITPROC` 那个静态引用），值得记住。

## 11.6 那个经典 bug：忘记关自己那份

管道编程里最经典的错误是这样的：

```rust
// shell 里
pipe(&mut fds);
fork(); // 子进程 A：dup 写端到 stdout
fork(); // 子进程 B：dup 读端到 stdin
// ← 忘了在这里 close(fds[0]) 和 close(fds[1])
waitpid(...);  // 永远等不到 B 结束
```

shell 自己不参与数据传输，但**只要它还握着写端，"所有写端都关了"就永远
不成立**，末端的 `14wc` 会一直等下去，整条管道死锁。

同样的道理也适用于每个子进程：它们必须关掉管道 fd 的原始副本
（已经 dup 到 0/1 了），否则自己就持有着写端。

所以 `run_command` 里有两处 `close` 循环，缺一不可：

```rust
// 子进程里
for p in pipes.iter().take(n - 1) { close(p[0]); close(p[1]); }
// 父进程里
for p in pipes.iter().take(n - 1) { close(p[0]); close(p[1]); }
```

`15pipetest` 把这件事单独演示了一遍：父写子读，两边各自关掉不用的那一端。

## 11.7 缓冲区故意开得很小

```rust
const RING_SIZE: usize = 32;
```

32 字节很容易被写满，这样"**写端阻塞等读端**"这条路径在日常使用中就会被
真实地走到，而不是一个从没被测试过的分支。

`15pipetest` 写 52 字节：

```
  [管道·父] 写入 52 字节（管道缓冲区只有 32 字节）
  [管道·子] 收到 16 字节：abcdefghijklmnop
  [管道·子] 收到 16 字节：qrstuvwxyz012345
  [管道·父] 写完了，返回 52
  [管道·子] 收到 16 字节：6789ABCDEFGHIJKL
  [管道·子] 收到 4 字节：MNOP
  [管道·子] 读到 EOF，共 52 字节
```

看那个交错顺序：父进程写到第 32 字节时缓冲区满了，于是它挂起等子进程
取走，取走之后才继续写完剩下的 20 字节。**流控是自动发生的** ——
这正是管道比"一个大数组"高明的地方：它天然限制了生产者跑在消费者前面
多远，内存占用是有界的。

## 11.8 三级管道

```
ccnuos> 12words | 13upper | 14wc
3 行，63 字节
```

手算核对一下：

```
"hello from ccnuos\n"        18 字节
"pipes connect processes\n"  24 字节
"everything is a file\n"     21 字节
                             ─────
                             63 字节
```

对得上。三个进程、两个管道、数据流经两次跨地址空间的拷贝，
结果一个字节都不多不少。

## 11.9 一个没解决的问题：写端没人读

如果读端全关了，写端还在写，会怎样？

真实的 Unix 会给写进程发 `SIGPIPE`，默认行为是杀掉它 ——
这就是为什么 `yes | head -1` 不会一直跑下去。

我们还没有信号机制，所以只能退而求其次：检测到"读端全关"时让 `write`
返回已写出的字节数，并打一条错误日志。至少不会死锁，但语义不完整。

信号是个大话题（要改 trap 处理、要在返回用户态时检查待处理信号），
超出了 16 周的范围。**把没做的事明确记下来，比假装它不存在好。**

## 11.10 练习

1. **去掉 shell 里父进程那两行 `close`**，运行 `12words | 14wc`，
   观察它怎么挂住。这是 11.6 节那个经典 bug 的复现。
2. **去掉子进程里的 `close` 循环**，同样观察。想清楚这两处的区别。
3. **把 `RING_SIZE` 改成 4096**，重跑 `15pipetest`，看输出的交错顺序
   怎么变。理解"流控"是怎么随缓冲区大小变化的。
4. **实现 `sys_dup2(old, new)`**（把 `old` 复制到指定的 `new`），
   然后用它重写 shell 的重定向 —— 比"close 再 dup"更直白，
   也不依赖"返回最小空闲 fd"这条规定。
5. **给管道加上 `SIGPIPE` 的简化版**：读端全关时让 `write` 返回 -1，
   用户库看到 -1 就调 `exit`。想清楚这和真正的信号差在哪。
6. **测一测吞吐**：写一个程序通过管道传 1 MiB，用 `get_time` 计时，
   算一算每字节的开销。大头在哪 —— 系统调用、地址翻译、还是拷贝？
