# 第 12 章　块设备与块缓存

> 对应 tag `v0.12`。本章代码：`git diff v0.11..v0.12`
>
> 这一章开始接触真实外设，也第一次让代码离开 QEMU 跑测试。

## 12.1 一个第 1 周就立下的决定

第 1 周排计划时我写过一条：

> 文件系统建议**独立成一个 crate**（`easy-fs`），用一个 `BlockDevice` trait
> 隔离底层。好处是可以在宿主机上用普通文件模拟块设备，写标准的
> `cargo test` —— 不用每次都进 QEMU 调试。这一条能省下 10 小时以上。

这一章兑现了它。`easy-fs` 是个独立 crate，它的全部外部依赖就是一件事：

```rust
pub trait BlockDevice: Send + Sync + Any {
    fn read_block(&self, block_id: usize, buf: &mut [u8]);
    fn write_block(&self, block_id: usize, buf: &[u8]);
}
```

于是同一份代码有了三个使用者：

| 谁 | `BlockDevice` 的实现是 |
|---|---|
| 内核 | virtio-blk 驱动 |
| 镜像制作工具 `easy-fs-fuse` | 一个普通文件 |
| 单元测试 | 一段内存 |

```
$ make test
running 8 tests
test tests::位图分配与回收 ... ok
test tests::缓存命中不再碰设备 ... ok
test tests::多次修改只回写一次 ... ok
test tests::淘汰时自动回写 ... ok
...
test result: ok. 8 passed; finished in 0.00s
```

**0.00 秒。** 对比一下另一条路：改一行 → 编译内核 → 启动 QEMU →
肉眼在串口输出里找线索。效率差一个数量级，而且断言失败时什么信息都没有。

顺带一个好处：镜像制作工具和内核**共用同一份格式化代码**，
所以不可能出现"制作工具和内核对磁盘布局的理解不一致"这种问题。

## 12.2 块缓存的两个关键设计

### 写回，不是写穿

修改只改内存里的副本，打上"脏"标记，等这个缓存项被淘汰时才真正写磁盘。

好处是**连续多次修改同一个块只产生一次磁盘写**。测试直接量出来了：

```rust
for i in 0..20u32 {
    get_block_cache(2, dev.clone()).lock().modify(0, |v: &mut u32| *v = i);
}
assert_eq!(disk.writes(), 0, "写回策略下，修改不该立刻产生磁盘写");

sync_all_blocks();
assert_eq!(disk.writes(), 1, "20 次修改应该合并成 1 次磁盘写");
```

代价是**掉电会丢数据**。所以必须提供 `sync_all_blocks()`，
让上层在关键时刻强制落盘。这不是可选的便利函数，是写回策略的必要配套。

### 用 `Drop` 触发回写

```rust
impl Drop for BlockCache {
    fn drop(&mut self) { self.sync(); }
}
```

缓存项被淘汰时自动写回，不需要在每个淘汰点手写一遍。

**这个项目里 RAII 已经用第四次了**：页帧（第 6 章）、PID 和内核栈（第 9 章）、
文件对象（第 10 章），现在是脏块。规律很清楚 —— 凡是"忘了释放会造成
慢性问题、而释放点又有好几处"的资源，都该交给 `Drop`。

### 缓存池故意开得很小

```rust
const CACHE_LIMIT: usize = 16;   // 8 KiB
```

和第 11 章把管道缓冲区开成 32 字节是同一个考虑：**让 LRU 淘汰和脏块回写
这两条路径在日常使用中就被真实走到**，而不是一组从没被测试过的分支。

淘汰时有一个约束值得注意：

```rust
let victim = self.queue.iter()
    .position(|(_, c)| Arc::strong_count(c) == 1)
    .expect("块缓存全被占用，无法淘汰");
```

`strong_count == 1` 意味着只有缓存池自己拿着它。**有人正拿着的块不能扔** ——
扔了会触发 `Drop` 回写，而持有者手里那份还在被修改，两边就打架了。

## 12.3 virtio-blk：第一个真正的驱动

前面所有的"外设"其实都是请 SBI 固件代劳的（串口、时钟）。
这是第一次内核直接跟硬件寄存器对话。

### virtqueue

驱动和设备之间靠三张表通信：

```text
  描述符表 (desc)    一个个"内存片段"：地址、长度、标志、下一个是谁
       ▲                    ▲
       │                    │
  可用环 (avail)        已用环 (used)
  驱动写，设备读        设备写，驱动读
```

一次请求：

1. 在 **desc** 里串起三个片段：请求头 → 数据缓冲 → 状态字节
2. 把链头编号写进 **avail** 环，`avail.idx += 1`
3. 往 `QueueNotify` 写一下，踢设备一脚
4. 设备处理完，把编号放进 **used** 环，`used.idx += 1`
5. 驱动看到 `used.idx` 变了就知道好了

我们用**轮询**等第 4 步。引入设备中断需要 PLIC 驱动，那是第 14 章的事；
而文件系统操作本来就不频繁，轮询的浪费可以接受。

### 三个片段的方向不一样

```rust
desc[1] = Descriptor {
    addr: buf,
    flags: if write { DESC_F_NEXT } else { DESC_F_NEXT | DESC_F_WRITE },
    ...
};
```

`DESC_F_WRITE` 的含义是"**设备写、驱动读**"。所以：

- **读磁盘**时，数据缓冲要打上这一位（设备往里填数据）
- **写磁盘**时不能打（设备从里面取数据）

方向搞反的话，设备会往你的数据上写垃圾，或者把随机内存写进磁盘。
这一位的语义是从设备视角定义的，很容易想反。

### 内存屏障不是装饰

```rust
(*queue).avail.ring[slot] = 0;
fence(Ordering::SeqCst);
(*queue).avail.idx = (*queue).avail.idx.wrapping_add(1);
```

必须保证"填好描述符"的所有写都对设备可见之后，才更新 `idx`。
少了这道屏障，设备可能看到一个已经递增的 `idx`，却读到还没写完的描述符 ——
症状是偶发的数据损坏，而且只在特定的编译器优化级别和硬件上出现。

## 12.4 恒等映射的第二个好处

设备做 DMA 时用的是**物理地址**，它不认识页表。

而第 7 章建内核地址空间时把所有物理内存都做了恒等映射
（虚拟地址 = 物理地址），所以**任何内核指针的数值本身就是物理地址**，
直接传给设备即可：

```rust
unsafe { self.request(block_id, buf.as_mut_ptr() as usize, false) }
```

当时选恒等映射的理由是"简单、方便内核读写任意物理页"。到这一章才显出
第二个好处 —— 它让 DMA 变成了一件不需要额外考虑的事。

virtqueue 本身也放在 `.bss` 里而不是从页帧分配器要：这样它天然是
物理连续的（规范要求），地址也天然是物理地址。

还要补一件事：**MMIO 寄存器也得在页表里有映射**。它不是"内存"，
但 CPU 要用普通的 `load`/`store` 去访问。所以内核地址空间多了一段：

```rust
add("MMIO 设备寄存器", mmio_start, mmio_end, r | w);
```

`R | W`，不带 `X` 也不带 `U`。

### legacy 还是 modern

virtio-mmio 有两个版本，队列配置方式完全不同：

- **v1（legacy）**：整个队列必须页对齐且连续，告诉设备一个页框号
- **v2（modern）**：三张表可以分开放，各给一个 64 位物理地址

驱动里两种都实现了，靠读 `Version` 寄存器分派。实测 QEMU 11 的 virt 机器
给的是 **v1**：

```
[INFO] virtio-blk：槽位 0（0x10001000），MMIO v1，容量 4096 扇区（2048 KiB）
```

不过既然规范里两种都有，只支持一种就是在赌 —— 换个 QEMU 版本或者别的模拟器
就可能翻车。四十行代码买一个确定性，划算。

## 12.5 验收：读通了，也写通了

挂载检查证明**读**路径没问题：

```
[INFO] 文件系统已挂载，魔数 0x43434e55：
[INFO]   超级块        块 0
[INFO]   索引节点位图  块 1..2
[INFO]   索引节点区    块 2..34
[INFO]   数据块位图    块 34..35
[INFO]   数据块区      块 35..4096
[INFO]   共 4096 块（2048 KiB）
```

每一项都和 `easy-fs-fuse` 制作镜像时打印的完全一致。

但读通了不等于写通了。所以又加了一个**跨重启的启动计数器**：
往数据区第一块写一个计数，落盘，下次开机读出来加一。连开三次：

```
[INFO] 持久化自检：这是这块盘的第 1 次启动（计数已写入块 35）
[INFO] 持久化自检：这是第 2 次启动 —— 上次写的数据确实留在磁盘上了
[INFO] 持久化自检：这是第 3 次启动 —— 上次写的数据确实留在磁盘上了
```

这一条同时证明了三件事：写路径正确、`sync_all_blocks()` 真的落盘了、
数据在 QEMU 进程退出后仍然存在。

> 顺带说一句，`sync_all_blocks()` 这一句**不能省**。写回策略下，
> 不显式落盘的话这次修改只存在于内存里，QEMU 一退出就没了 ——
> 而且症状是"程序看起来完全正常，只是数据莫名其妙不见了"。

## 12.6 一个有意留下的简化

块缓存只按**块号**索引，不区分设备：

```rust
pub fn get_block_cache(block_id: usize, device: Arc<dyn BlockDevice>) -> ...
```

传进来的 `device` 只在未命中时用来读盘。如果系统里有两块盘，
它们的第 0 块会互相串台。

本项目只有一块盘，所以这是个安全的简化。但它写在了
`clear_block_cache()` 的文档里，免得以后有人加第二块盘时踩坑。
**把简化的边界记下来，比假装它不存在好。**

1. **去掉 `persistence_check` 里的 `sync_all_blocks()`**，连开两次，

6. **统计一次完整启动的块 I/O**：在 `MemDisk` 之外给 virtio 驱动也加上
   读写计数，开机后打印。和 `block_cache_stats()` 的命中率对照。
