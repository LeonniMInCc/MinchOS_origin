# 第 13 章　文件系统

> 对应 tag `v0.13`。本章代码：`git diff v0.12..v0.13`
>
> 阶段 III 完成。做完之后，内核不再自带用户程序 —— 它们都在磁盘上。

## 13.1 兑现一个写了三章的承诺

第 10 章定义 `File` trait 时写过：

> 有了 trait，那两章只要多写一个实现，`sys_read` / `sys_write`
> 一行都不用改。

第 11 章加了管道，这一章加了磁盘文件。**`sys_read` / `sys_write`
从第 10 章写完之后，一行都没有动过。**

```text
                 ┌── Stdin / Stdout   （第 10 章，串口）
  File trait ────┼── Pipe             （第 11 章，环形缓冲）
                 └── OSInode          （第 13 章，磁盘 inode）
```

这就是 Unix "一切皆文件"那句话的技术含义：不是"所有东西都存成文件"，
而是**所有东西都用同一组动词来操作**。

## 13.2 inode：直接块加间接块

一个文件的内容散落在若干数据块里，inode 得记住是哪些。直接列出来的话，
大文件的 inode 会非常大 —— 而绝大多数文件都很小。

所以用两级：

```text
  direct[0..27]  ──▶ 数据块          覆盖 13.5 KiB 以内
  indirect1      ──▶ [块号 × 128] ──▶ 数据块     再多 64 KiB
```

`DiskInode` 刻意凑成 **128 字节**，这样一个 512 字节的块正好放 4 个，
不会出现"一个 inode 横跨两个块"这种恶心情况。

代价是访问大文件的后半部分要多读一次盘。真实文件系统会做到三级间接，
原理完全一样。

## 13.3 目录就是一个普通文件

这是 Unix 的一个关键简化：**目录的内容就是一串目录项**，用和普通文件
完全相同的 `read_at` / `write_at` 存取。

```rust
pub struct DirEntry {
    name: [u8; 28],
    inode_id: u32,
}   // 32 字节
```

于是"在目录里新建一个文件"就变成了：

```rust
self.modify_disk_inode(|dir| {
    let old_size = dir.size as usize;
    self.grow(dir, (old_size + DIRENT_SZ) as u32);   // 目录也会扩容
    dir.write_at(old_size, entry.as_bytes(), &self.device);
});
```

不需要为目录发明单独的存储结构。这种"用已有抽象表达新概念"的做法，
在这个项目里已经出现很多次了 —— 启动程序 = 从 trap 返回（第 3 章）、
`ra` 的两种语义（第 4 章）、三条路径一个调度器（第 5 章）。

## 13.4 内核不再自带用户程序

第 3–12 周，用户程序是被 `build.rs` 用 `.incbin` 嵌进内核 `.data` 段的 ——
那时没有文件系统，内核没有任何办法"读取"一个程序。

现在有了。`exec` 改成从磁盘读：

```rust
let Some(data) = read_file(&path) else { ... };
```

于是 `link_app.S`、`loader.rs`、以及 `build.rs` 里生成它们的那段逻辑
**一起退休了**。效果很直观：

| | 第 12 周 | 第 13 周 |
|---|---|---|
| 内核镜像 | 343 KiB | **123 KiB** |
| 换用户程序 | 重新编译内核 | 只重做镜像 |

后一条才是真正的收获。这也是为什么真实系统的内核里没有 `/bin/ls`。

## 13.5 重定向：欠了两章的债还上了

第 11 章做管道时，`>` 被推迟了，因为"输出得有地方去"。现在有了：

```rust
let (program, redirect) = split_redirect(stages[i]);
if let Some(path) = redirect {
    close(STDOUT);
    open(path, WRONLY | CREATE | TRUNC);   // 新 fd 必然落在 1 上
}
exec(program);
```

**手法和管道完全一样**：关掉 fd 1，再打开目标，新 fd 必然是最小的空闲号，
也就是 1。程序自己完全不知道它的输出去了哪里。

第 11 章我写过"到时只需把 `dup(pipe_write)` 换成 `dup(file_fd)`"——
实际更简单，`open` 直接就返回 1，连 `dup` 都省了。

## 13.6 这一章最值钱的一个 bug

写完之后一跑，内核在 exec 时崩了：

```
[KERNEL PANIC] 只能在目录里查找：inode 位于块 2 偏移 0，size=0，type=0
```

根 inode 读出来**全是零**。但挂载时它明明是好的 —— 根目录列出了 21 个文件。

### 定位过程

先写了一个宿主机测试复现"建 21 个文件后再建一个，然后还要能找到原来的"——
**测试通过了**。所以文件系统逻辑没问题，是内核特有的路径。

然后关掉 `persistence_check`（唯一会写盘的地方）—— **还是崩**。所以也不是写坏的。

关键线索在崩溃的时机：

| 什么时候 | 结果 |
|---|---|
| 挂载、`read_file("initproc")` | ✅ 正常 |
| 进程里 `exec("user_shell")` | ❌ 读到全零 |

前者跑在**内核的启动栈**上，后者跑在**进程的内核栈**上。

### 根因

`BlockCache::new` 把一个**栈上的局部数组**交给设备做 DMA：

```rust
fn new(block_id: usize, device: Arc<dyn BlockDevice>) -> Self {
    let mut data = [0u8; BLOCK_SZ];      // ← 在栈上
    device.read_block(block_id, &mut data);
    ...
}
```

而驱动直接把这个指针当物理地址用了。这在第 12 章是成立的 ——
**但只对恒等映射的内存成立**。

**从第 8 章起，进程的内核栈是 `Framed` 映射在内核地址空间的高地址处的，
和物理地址毫无关系。** 设备拿到 `0xffff_ffff_ffff_d800` 这样的"物理地址"，
往一个根本不存在的地方写，而调用方看到的缓冲区**保持全零**。

第 12 章没暴露，纯粹是因为那时所有块 I/O 都发生在初始化阶段 ——
启动栈在 `.bss` 里，是恒等映射的。

### 修法与教训

加一块静态的 **DMA 中转缓冲区**（bounce buffer），DMA 只对着它做，
前后各拷贝一次。真实驱动在缓冲区不可 DMA 时干的也是同一件事。

```rust
#[repr(C, align(512))]
struct Bounce([u8; BLOCK_SZ]);
static mut BOUNCE: Bounce = Bounce([0; BLOCK_SZ]);
```

教训有两条，都值得写下来：

**一、"内核指针即物理地址"是一个有例外的规律，而我把它当成了规律。**
第 12 章的文档里我写的是"任何内核指针的数值本身就是物理地址"——
那句话是错的。已经改掉了（见 [ch12.md](ch12.md) 12.4 节的警告框）。
**一个只在大部分情况下成立的假设，比一个明显错误的假设更危险。**

**二、宿主机测试通过恰恰是有价值的信息。** 它没能抓到这个 bug，
但它把嫌疑范围从"整个文件系统"一口气缩小到了"内核特有的路径"。
排除法本身就是进展。

## 13.7 验收：重启之后文件还在

第一次启动，写一个文件、再用重定向写一个：

```
ccnuos> 17write
write: 往 readme.txt 写了 42 字节（时间戳 1894 ms）
ccnuos> 16cat
CCNUOS file system works.
written at 1894
cat: 共 42 字节
ccnuos> 12words > out.txt
```

**关掉 QEMU，重新启动**，什么都不写：

```
[INFO] 持久化自检：这是第 2 次启动 —— 上次写进 bootcount 的内容确实留在磁盘上了
ccnuos> 18ls
  ...
  bootcount
  readme.txt
  out.txt
共 24 个文件
ccnuos> 16cat
CCNUOS file system works.
written at 1894          ← 还是上一次那个时间戳
cat: 共 42 字节
```

时间戳没变，说明读到的确实是上次写进去的那份，而不是这次新生成的。

一整轮下来页帧零泄漏。

## 13.8 几处有意的简化

写下来，免得以后误以为它们已经解决了：

- **只有一层扁平的根目录。** 没有子目录、没有路径解析。
  加子目录本身不难（`DiskInode` 已经有 `Directory` 类型了），
  但路径解析、`.`/`..`、当前工作目录是一整套东西
- **`sys_listdir` 不是 POSIX。** 真实系统用 `getdents` 返回结构化的目录项。
  我们只有十几个文件，直接给一串换行分隔的名字够用了 ——
  **接口的复杂度应该配得上需求**
- **没有 `lseek`。** `OSInode` 的读写位置只能顺着走。
  `persistence_check` 里"重新 open 一次以回到文件开头"就是这个缺口的痕迹
- **没有删除。** `Inode::clear` 能清空内容并归还数据块，但目录项和 inode
  还在。实现 `unlink` 要处理目录项的紧缩

## 13.9 练习

1. **实现 `sys_lseek`**，然后把 `persistence_check` 里那次"重新 open"
   换掉。这是最值得先做的一个。
2. **实现 `unlink`**：从目录里摘掉一条目录项、回收 inode 和数据块。
   想清楚目录项数组该怎么紧缩（提示：把最后一条挪过来最省事）。
3. **给 `exec` 加上命令行参数**，然后让 `16cat` 能接文件名。
   这需要把 argv 压进新进程的用户栈 —— 挺有意思的一道题。
4. **支持 `>>` 追加**：和 `>` 的区别只在于不要 `TRUNC`，
   并且打开后要把位置挪到末尾（需要第 1 题的 `lseek`）。
5. **实现子目录**：`mkdir`、路径解析、`.` 和 `..`。
   这是把这个文件系统变成"真的能用"的最后一大步。
6. **测一测块缓存的效果**：连续 `16cat` 同一个文件十次，
   看 `block_cache_stats()` 的命中率。再把 `CACHE_LIMIT` 调小重测。

## 13.10 阶段小结

**阶段 III（文件与交互）到此完成**：

| 周 | 成果 |
|---|---|
| 10 | `File` trait、文件描述符表、`sys_read`、交互式 shell |

CCNUOS 现在是一个**能交互、有进程、有内存隔离、有持久化存储**的操作系统。
用户程序不在内核里，命令可以用管道串起来，输出可以重定向到文件，
文件在重启后还在。

第 15 周做教学可视化，第 16 周收尾交付。

`waitpid` 的 -2 重试（第 9 章）、以及没有输入缓冲导致的丢字符（第 10 章）——
