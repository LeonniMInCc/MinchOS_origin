CCNUOS

用 Rust 从零写一个 RISC-V 操作系统

16 周 · 单人 · 零外部依赖 · v1.0

01它到底能做什么

从上电开始接管机器，建立虚拟内存，把程序从自己的文件系统里读出来、 装进各自独立的地址空间执行，抢占式地分配 CPU， 让它们通过管道和同步原语协作 —— 并在它们越权时拦住它们。

ccnuos> 12words | 13upper | 14wc     ← 三级管道
ccnuos> 12words > out.txt            ← 重定向，写进真实磁盘
ccnuos> 19philosophers              ← 五个进程 + 信号量
ccnuos> 10bad_kernel_write          ← 越权进程被杀，内核毫发无损

最终形态是一个可交互的 shell，23 个演示程序跑在上面。

04核心设计：用 RAII 管内核资源

物理页帧、PID、内核栈、打开的文件、脏缓存块 —— 全部由 Drop 负责归还。

传统内核里「分配后忘了释放」是最常见的一类 bug，而且症状离病因极远： 几小时后内存耗尽，病因是某个错误分支提前 return。

把归还绑在类型的析构上之后，这类 bug 在编译期就不可能写出来。

# 内核关机前自动核对，端到端验证整条 RAII 链
[INFO ] 页帧核对：72 页，与用户态启动前完全一致，无泄漏

这条检查在第 9 周报过一次警，查出是静态变量仍持有 PCB —— 说明它真的在工作。

05核心设计：内核不可抢占

代价

  • 内核里的长操作会推迟中断响应

收益

  • UPSafeCell 得以成立
  • 「先入队、再睡下」不需要额外的锁
  • 一条日志不会被打印到一半

这是单核教学系统上的正确取舍。

多核下会立刻失效 —— 所以文档里明确写了这一点， 而不是留给读者去踩。

把简化写出来，和把它藏起来，
是两种完全不同的工程态度。

06核心设计：一组动词，三种实现

trait File {
    fn readable / writable / read / write
}

标准输入输出、管道、磁盘文件都实现它。

于是 shell 的重定向和管道不需要知道 fd 背后是什么东西：

ccnuos> 12words | 13upper > out.txt

这条命令能工作，没有为它写过一行特判。

Unix「一切皆文件」的收益，在这里是具体的。

07最有价值的一个 bug

第 16 周的回归测试，第一次跑就抓到一个潜伏四周的数据丢失。

写 42 字节 → 关机 → 重启 → 读
cat: 共 0 字节          ← 文件在，内容没了

原因：块缓存是写回式的，落盘发生在缓存项被淘汰时。缓存没满就一个块都不写。 而内核关机时从来没调用过 sync_all_blocks。

为什么四周没发现：唯一证明「落盘了」的证据是启动计数器， 而它恰好在写完后自己同步了一次。用户文件从未真正持久化 —— 但同一次运行里读当然读得到（缓存命中），所有演示都「正常」。

「同一次运行里能读到」证明不了持久化。
想验证落盘，测试就必须跨越一次关机。

08另外两个改变了我理解的坑

DMA 到内核栈，读出来全是 0（第 13 周）

把栈上的数组地址当物理地址交给设备。启动期间栈在 .bss（恒等映射）所以碰巧对； 第 8 周内核栈改成高地址 Framed 映射后，这个等式不再成立。 设备看到的地址空间和 CPU 看到的不是一回事 —— 恒等映射让这个区别暂时消失， 然后在某个不相干的改动之后突然回来。

错误日志里的整数溢出（第 3 周）

error!("非法缓冲区 [{:#x},{:#x})", buf, buf + len);

用户传一个巨大的 len，release 下悄悄回绕，debug 下在处理恶意输入的代码里 panic。 错误处理路径也在信任边界上。

09三层测试，反馈速度差三个数量级

层次范围怎么跑耗时
单元测试easy-fs 内部逻辑make test（宿主机）0.01 s
内核自检堆 / 页帧 / 页表 / 地址空间每次启动自动跑启动时
回归测试23 个程序端到端make regress（QEMU）约 2 min

文件系统做成独立 crate，只依赖一个 BlockDevice trait， 所以能在宿主机上用内存模拟块设备 —— 全项目回报率最高的一个决定， 文件系统的调试基本没进过 QEMU。

10回归测试：把失败条件写进被测对象

每个用例 = 一串喂给 shell 的命令 + 两类断言。must_not 是更值钱的一半：

// 用户程序自己知道什么是失败
println!("如果你看到这行，说明内核没拦住我 —— 那是个严重问题。");

测试只要盯着这句话有没有出现，不必理解它在干什么。 把失败条件写进被测对象自己，比写进测试脚本更不容易腐坏。

通过  内存隔离：非法系统调用参数
通过  特权隔离：用户态执行 sret
通过  死锁必须被发现，而不是伪装成正常关机
通过  持久化：重启后文件内容原样还在

结果：16/16 通过

11教学可视化：内核说事实，脚本画图

@EV sched t=123456 pid=2
@EV sys   t=123460 pid=2 id=64
@EV area  t=123470 pid=2 vpn=0x10 pages=2 ppn=0x80a12 perm=R-XU

内核不知道甘特图的存在，脚本不知道 TaskControlBlock 长什么样。 两边只通过那一行文本耦合 —— 可视化推翻重写三次，内核一行没动。

渲染出四张图：调度甘特图、系统调用时序、进程树、地址空间对照。

地址空间那张一眼讲完分页：同一个程序在不同进程里虚拟地址完全一样，物理页号完全不同。

12观测者效应，是个能测出来的数

事件走串口，每字符一次 SBI 调用。从事件自身的时间戳就能量出成本 —— area 事件在一个循环里连着打，相邻间隔就是打一条的代价：

每字符 3.92 µs → 本次 23720 字符 ≈ 93 ms 输出开销
同一次运行 CPU 实际忙                        153 ms

→ 61% 的 CPU 时间花在打印「CPU 在干什么」上

所以事件输出由编译期常量控制。关闭时 LLVM 整段消除 —— 这一条验证过而不是想当然：关闭时二进制里连 @EV 这三个字符都不存在。

14做对的，和做得不够的

做对的

  • 每周一个可运行的版本，bug 引入点永远在一周内
  • 文件系统独立成 crate，秒级反馈
  • 把坑写下来 —— 报告里最有价值的一节全来自当周文档

做得不够的

  • 回归测试来得太晚。第 16 周第一次跑就抓到潜伏四周的 bug； 第 10 周就有的话，它活不过一周
  • 可视化可以更早 —— 甘特图对理解调度的帮助远超读代码
  • 性能没有系统测量过
测试基础设施的价值，与引入时间成反比。
